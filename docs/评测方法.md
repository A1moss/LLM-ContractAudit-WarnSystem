# 评测方法

> 三套正式评测的脚本、输入、计算公式与**冻结指标**。公式以 `backend/evaluate/` 下脚本的实际实现为准。
> **冻结指标与本口径不得因单次重跑结果不同而改写。**

---

## 一、总览

| 评测 | 正式脚本 | 输入 | 正式指标（冻结） |
|---|---|---|---|
| **法理分类** | `evaluate_rag.py` | `classification_test.json`（**147** 条） | **98.6%（145/147）** |
| **要素抽取** | `evaluate_elements.py` | `realtest.json`（**84** 份） | **93.7%**（P **94.8%** / R **92.7%**） |
| **风险识别** | `evaluate_evidence.py` | `realtest.json` + `evidence.json`（**84** 份） | **P 76.6% / R 80.1% / F1 78.3%** |

三套评测均走 DeepSeek `deepseek-chat`；温度：**分类 0.1**、**要素 0.0**、**证据抽取 0.0**。
分类与要素抽取带 MD5 缓存（`cache_elements.json` / `rag_predictions.json`），可复跑。

### 1.1 与正式指标配套的四个「必须同时说明」

1. **风险 F1 只覆盖 R01–R12**（`evaluate_evidence.py` 的 `STRICT = {R01…R12}`）；**R13 不进严格 F1**。
2. **R05 没有 Gold**，因此不存在 R05 的 P/R/F1（详见 [`数据集说明.md`](./数据集说明.md) 第四节）。
3. **严格 Gold 为 151 条**（152 条总量减去 1 条 R13）；实测 TP 121 + FN 30 = 151，与 Gold 自洽。
4. **R08 / R09 的 Gold 覆盖存在结构性限制**（缺失型风险，部分来自公开披露合同的构造补全条款），这两类的 P/R 解释力弱于显式命中型风险。

### 1.2 非正式脚本（**不得当作正式指标来源**）

| 脚本 | 性质 |
|---|---|
| `evaluate_classifier.py` | 纯 LLM 零样本分块投票分类的**基线对照**，脚本自身注明「数字不用于正式指标」。它用的**不是**生产默认的 RAG 少样本分类链。 |
| `evaluate_risks.py` | **双引擎六列对照评测**（fast 规则引擎 / precise 规则+LLM 直审），用于风险引擎演进对照与 FP 归因，**不是**正式风险指标来源。 |

## 二、分类评测（`evaluate_rag.py`）

### 输入

`classification_test.json`（**147** 条 = 84 第一批 + 55 第二批 + 8 人工构造边界样本；正文已去答案元信息并脱敏，Gold 冻结）。

### 流程

对每条调用生产同款分类函数：

```python
classify_by_rag(body, top_k=3, exclude_self=body)
```

即 **RAG 少样本分类**：在合同范本库检索 top-3 相似范本作为少样本示例喂给 LLM（temperature=0.1），`exclude_self` 用于防止评测时检索到自身。预测 `contract_type` 与 `true_type` 比对。

### 指标

- 准确率：`acc = 正确数 / 总数`
- 每类 P / R / F1：`P = 该类预测正确的样本数 / 预测为该类的样本数`；`R = 该类预测正确 / 该类真实样本数`；`F1 = 2PR/(P+R)`

### 输出

准确率 + 每类 P/R/F1 + 判错样本清单 + 预测快照 `rag_predictions.json`。

### 正式口径

**98.6%（145/147，判错 2：技术合同 1 + 劳动合同 1）**。

历史口径 **97.62%（82/84，84 份原测试集）** 保留作版本对照。

### 波动与留痕（如实披露）

分类使用 temperature=0.1，**结果存在 145↔147 的轻微波动**。本地评测缓存中的 `rag_predictions.json` 记录的是 **146/147（99.32%）** 的一次运行。

按既定原则，**正式口径冻结在 98.6%（145/147）**，不因内部重跑出现更高结果而替换。

## 三、要素评测（`evaluate_elements.py`）

### 输入

`realtest.json`（**84** 份）。对每份调用 `extract_elements(body, true_type)`，抽取四要素：`parties`（双方）、`amount`（金额）、`performance_period`（期限）、`dispute_resolution`（争议解决）。

### 比对口径（严格值级比对）

**只统计 Gold 中 `present == true`（可见文本实际披露）的要素**，然后做值级比对：

| 要素 | 匹配规则 |
|---|---|
| `parties` | 甲方、乙方均存在且不含「未知」（**不比对具体名称**——正文已脱敏） |
| `amount` | 归一化到「元」后比较，**10% 容差** |
| `performance_period` | **年份集合必须有交集**（「X 个月」这类描述无法通过） |
| `dispute_resolution` | 关键词命中（法院 / 仲裁 / 诉讼 / 国际商会 / 仲裁院 / 仲裁委员会）或文本完全相等 |

### 指标

对每个字段**在其披露样本上**计算：

```
TP / FP / FN  →  P = tp / (tp + fp)  →  R = tp / 披露样本数  →  F1 = 2PR/(P+R)
```

**刻意设计**：`pred` 非空但比对不命中（抽到了但值错）时，**同时计入 FP 与 FN**。因此精确率的分母 `tp + fp` 与召回率的分母（披露样本数）**不同** —— 这是严格 F1 的刻意取舍，不是 bug。

### 披露样本数（实测分母）

| 要素 | 披露样本 | F1（冻结） |
|---|---|---|
| 双方 parties | 84/84 | **100.0%** |
| 金额 amount | 78/84 | **87.2%** |
| 期限 performance_period | 82/84 | **90.8%** |
| 争议解决 dispute_resolution | 84/84 | **96.3%** |

### 加权综合 F1（非标准宏平均）

脚本明确定义为**按各字段披露样本数加权的 P/R 反推 F1**：

```
w_p = Σ(field_p × field披露样本数) / Σ(field披露样本数)
w_r = Σ(field_r × field披露样本数) / Σ(field披露样本数)
w_f = 2 · w_p · w_r / (w_p + w_r)
```

### 正式口径（冻结）

**综合 F1 = 93.7%**，对应 **Precision = 94.8% / Recall = 92.7%**。

> 说明：加权 P/R 对（94.8% / 92.7%）不在脚本 stdout 的默认表格里（默认只打印各字段 P/R/F1 与加权 F1）；它是正式口径的配套数值，用于解释 93.7% 的来源。
> 由于公开披露合同的期限与争议解决披露率 <100%，严格 F1 **只在披露样本上计算**；要把它对齐到「全量 84 份」的分母，需要完整合同 + span 级标注。

### 历史口径（版本对照）

**90.7%**（加权 P 91.7% / R 89.6%；各字段 双方 95.2 / 金额 84.6 / 期限 85.9 / 争议解决 96.3）。保留作演进对照，不作为当前指标。

## 四、风险评测（`evaluate_evidence.py`）

### 输入

`realtest.json`（84 份）+ `evidence.json`（由 `run_evidence.py` 预计算的 LLM 证据抽取结果，84 个键）。

### 裁决

与**生产共用同一个裁决函数**：

```python
from ai.auditor.evidence_adjudicator import adjudicate_risks
pred = {r["risk_type"] for r in adjudicate_risks(rec["evidence"])}
```

即 **v6.4 的证据裁决口径，只裁决 R01–R12**。评测与生产共用同一份代码，消除历史上「评测内置一份复制版」导致的口径错位。

### 比对

逐份合同做集合比对，`STRICT = {R01…R12}`：

```python
gold = {r["risk_type"] for r in entry["risks"] if r["risk_type"] in STRICT}
pred = adjudicate_risks(entry["evidence"]) 的 risk_type 集合
```

**无风险合同（Gold 为空）也必须参与评测** —— 否则会漏掉它们的过报（FP），导致精准率被系统性高估。当前有 **33 份无严格 Gold 的合同**参与评测。

### 公式

```
TP = Σ|gold ∩ pred|      （gold 且预测正确）
FP = Σ|pred \ gold|      （多报）
FN = Σ|gold \ pred|      （漏报）
P  = TP / (TP + FP)
R  = TP / (TP + FN)
F1 = 2·P·R / (P + R)
```

### 正式口径（冻结）

| 指标 | 值 |
|---|---|
| TP | **121** |
| FP | **37** |
| FN | **30** |
| Precision | **76.6%** |
| Recall | **80.1%** |
| F1 | **78.3%** |

自洽性核对：`121 + 30 = 151` = R01–R12 严格 Gold 总数 ✓（见 [`数据集说明.md`](./数据集说明.md) 第 4.1 节）。

### 输出

stdout：总体 P/R/F1 + 分类别 P/R + 完整 FN / FP 明细（无结果文件）。

## 五、R13 与双引擎对照（`evaluate_risks.py`，非正式口径）

`evaluate_risks.py` 是**双引擎六列**评测：

- **fast**：`rule_engine.run_rules`；
- **precise**：`rule_engine.run_rules` ∪ `llm_auditor.audit_with_llm`（temperature 0）。

其中：

- `STRICT_TYPES = {R01…R12}`，**R13「疑似名实不符」单列示警，不进严格 F1**；
- 采用**两套词汇表**：开放集（全部 R01–R12）与闭集（`pred ∩ gold_vocab`，即只在 Gold 出现过的类型里算）；
- 置信度阈值 `[None, 0.6, 0.7, 0.8]` 只用于裁剪**仅由 LLM 检出**的类型，规则命中始终保留；
- LLM 结果按 `md5(body)[:16]` + `PROMPT_VERSION` 缓存于 `cache_risks_llm.json`。

用途：**风险引擎演进对照与 FP 归因**。正式风险指标仍以 `evaluate_evidence.py` 为准。

```bash
cd backend
```

## 八、评测真实性保障

1. **评测与生产共用裁决代码**：`evaluate_evidence.py` 直接 `import` 生产的 `adjudicate_risks`，不做第二份实现。
2. **官方评测路径不可被 Feedback RAG 注入**：`run_evidence.py` 调用的 `extract_evidence(full_text)` 签名不含 `feedback_context`，prompt 逐字节不变；有回归测试 `test_feedback_rag.py::test_eval_entry_ignores_enabled_flag` 断言。
3. **评测语料隔离闸**：`services/eval_isolation.py` 对三份评测语料做 sha256 指纹，**与其正文完全一致的合同**禁止沉淀为学习经验（全篇逐字判定）。
4. **无风险合同必须参与评测**：避免精准率被系统性高估。
5. **留痕**：分类有预测快照、要素有 MD5 缓存、风险证据有 `evidence.json`，均可复核。

## 九、评测数据构建与人工质检流程

> 本节说明「评测数据是怎么来的」。数量、分布与 Gold 结构见 [`数据集说明.md`](./数据集说明.md)；标注定义与边界规则见 [`风险标注与Gold规范.md`](./风险标注与Gold规范.md)。
> 团队分工统一以**角色**表述（采集人员 / 合同整理·还原人员 / 标注人员 / 审计人员），不涉及具体姓名。

### 9.1 总流程

```
公开合同材料
   ↓
候选采集
   ↓
公告 / 完整合同筛选
   ↓
必要时合同正文还原
   ↓
双人独立背对背标注
   ↓
第三人审计
   ↓
分歧复核
   ↓
最终人工裁决
   ↓
正式评测数据 / Gold
```

### 9.2 六个阶段（实际做法，含未做到的部分）

**第一阶段：候选采集**

- 由采集人员从**公开渠道**获取候选合同材料（政府采购网公开发布的已签署合同、上市公司公告及其附件等）；
- 实际采集中发现：公开来源里存在大量**「合同公告、采购公告、成交公告、结果公告、合同签订公告」**类材料。这类材料是交易信息的公告披露，**并不等同于完整合同正文**，**不能直接全部作为合同审核样本**。

**第二阶段：公告 / 完整合同筛选**

- 因此首先由人工逐份筛选，区分两类材料：
  - **完整 / 基本完整的合同正文**（可直接进入评测）；
  - **公告、摘要、结果信息等非完整材料**（需还原，或不得直接纳入）。
- 判定依据是材料的**实际性质**（招标/中标/结果公告 vs. 合同正文），不是标题。

**第三阶段：合同正文还原 / 整理（必要时）**

- 对确实需要使用、但公开页面只提供公告 / 碎片化信息的材料，在**能够可靠还原**的前提下，由合同整理·还原人员做正文还原／整理，目标是得到**可进行条款级审核**的正文材料；**无法可靠还原为合同正文的材料不纳入正式合同评测集**；
- 实际用到的还原手段（按材料形态）：
  - **PDF 文本层提取**（政府采购网已签署电子合同 PDF）；
  - **网页全文转写**（政府采购网 HTML 合同页面）；
  - **扫描件 OCR 转写**（扫描版合同 PDF，如北京 / 潍坊政府采购房屋租赁合同）；
  - **公告 → 披露版整理**：保留公告**真实披露**的条款内容并按标准章节重组，**公告未披露的章节标注「公告未披露」，不编造**；
- **无法可靠还原为合同正文的材料，不得为了扩大数据量而强行纳入正式合同评测集。**
- 如实说明：并非所有公告类材料都被成功还原；公告披露版合同在正文中**保留了「补全」标注**，其构造补全条款**不是公告原文**（详见 [`数据集说明.md`](./数据集说明.md) 第 3.3 节）。

**第四阶段：双人独立背对背标注**

- 两名标注人员**分别独立阅读合同**，在**互不查看对方标注结果**的情况下完成标注；**不允许先讨论后共同填写**——否则不构成背对背标注；
- 标注内容按项目既定评测口径执行：**合同类型（11 类法理 + 业务标签）、关键要素（双方 / 金额 / 期限 / 争议解决）、风险相关标签（R01–R13 + 条款要点说明）**；
- 标注人员**只依据标注规范与合同正文**判断，**不参考也不得使用任何模型 / 规则引擎输出**（这是 Gold 独立性的前提）。

**第五阶段：第三人审计与最终裁决**

- 由**审计人员**对标注结果进行审计，重点检查三项：**证据是否来自合同原文**、**标签是否符合既定定义**、**不同标注之间是否存在明显冲突**；审计**不是简单复制任一标注人的结果**；
- 对双人标注与审计发现的分歧逐条复核，按项目既定标注规则（R01–R13 定义 + 三条上位规则 A/B/C）做**最终裁决**，定标结果才进入正式 Gold / 评测口径；
- **最终裁决不是为了让模型结果更好，而是为了形成独立于模型输出的人工参考标准。**

### 9.3 实际达到的程度（如实说明，不夸大）

| 批次 | 份数 | 实际流程 | 是否有第二人独立盲标 |
|---|---|---|---|
| 第 3 批 | 10 | 一方标注压着 → 第二人独立盲标 → 互换对比 → 4 处分歧 → 仲裁定标 | ✅ **真背对背** |
| 第 7 批 | 10 | 一方落库 → 第二人比对 → 3 处漏标回写 | ⚠️ 事后比对（对照已定稿 Gold） |
| 第 8 批 | 14 | 一方落库 → 第二人盲标对照 → 14/14 一致 | ⚠️ 事后比对 |
| 第 1/2/4/5/6 批 | 50 | 主标方直接标定落库 | ❌ 无第二人独立盲标，仅事后回溯核查 |

- **能报告**：定稿 Gold 的数量与分布；上述过程本身；**合同级复核一致率 79.4%**（第 3+7+8 批共 34 份中 27 份完全一致、7 份存在分歧/漏标）；分歧定标记录；
- **不能报告**：**全量 84 份的 Cohen's κ / 互判 macro-F1 / micro-F1** —— 其中约 50 份没有第二人的独立盲标，硬算属「伪双人一致性」。
- 因此项目统一表述为「**双人交叉复核 + 分歧仲裁**」。该结果经双人独立标注、第三人审计和最终裁决形成，属**项目人工参考标准**，**不是**外部权威金标准。

### 9.4 来源结构（与 9.2 对应）

| 来源 | 份数 | 性质 |
|---|---|---|
| 上市公司公告披露版合同 | 47 | 公告真实披露核心条款 + 按行业惯例/官方范本构造的**补全**条款（标注「补全」，非公告原文） |
| 真实已签署政府采购合同 | 32 | 公开采购渠道；PDF 文本层提取 / 网页全文转写 / 扫描件 OCR 转写 |
| 人工构造 | 5 | 4 份劳动合同 + 1 份保密协议（公开渠道不可得，依法律构造并标注） |
| **合计** | **84** | 用于风险与要素评测；分类正式集另为 147 条 |

> 同一份来源清单也登记并公开了**被否决的渠道**（如公共资源交易平台超时、合同公告系统为 JS 空壳），不做无来源的样本填充。

### 9.5 评测与反馈经验的隔离原则（防止评测泄漏）

1. **正式评测集不能通过反馈经验机制反向污染评测**：任何来自评测语料的合同都不允许沉淀为「人工反馈经验」；
2. **评测隔离机制**：`services/eval_isolation.py` 对 `realtest.json`、`classification_test.json`、合同范本样本集三份受保护语料做归一化 sha256 指纹，**入库前比对，与语料正文完全一致即拒绝进入反馈经验沉淀**（全篇逐字判定，非片段级）；本仓库内的范本语料位置为 `backend/ai/rag/resources/contract_templates_source.json`；
3. **评测结果与人工 Gold 构建流程相互独立**：Gold 由标注人员独立形成，评测脚本只做「预测 vs Gold」的比对，不参与 Gold 的生成；
4. **不允许把模型预测结果作为人工 Gold 的依据**（`风险标注与Gold规范.md` 第 8.3 节定标纪律第 3 条）；
5. **不允许为了提升指标而修改 Gold 标签**：正式指标一经确定即冻结，内部重跑出现更高结果**不替换**正式口径；
6. **官方评测路径不可被反馈经验注入**：`run_evidence.py` 调用的 `extract_evidence(full_text)` 签名不含 `feedback_context`，prompt 逐字节不变（有回归测试断言）。
