> 所有数量均由数据文件实测得出（`backend/evaluate/*.json`）。**分类数据集与风险数据集必须严格区分，不得混用。**

### 2.2 类型分布（实测）

买卖合同 24、技术合同 17、物业服务合同 16、建设工程合同 15、租赁合同 14、无名合同 13、承揽合同 12、委托合同 11、劳动合同 10、中介合同 8、保密协议 7 —— 合计 **147**。

### 2.3 记录字段

```jsonc
{
  "id": "realtest_001",            // 或 batch2_<名称> / manual_边界样本-<名称>
  "true_type": "买卖合同",          // Gold 标签（11 类之一）
  "content": "…",                  // 已去答案元信息 + 已脱敏的正文
  "source": "第一批",               // 第一批 / 第二批 / 人工构造
  "source_file": "05_合同\\现实合同\\…\\xxx.md",
  "is_manual": false               // 人工构造样本为 true
}
```

### 2.4 构建方式（`build_classification_test.py`）

1. 第一批：直接取 `realtest.json` 的 84 条（保留 `id` 与 `true_type`）；
2. 第二批：遍历 `05_合同/现实合同/第二批合同/**/*.md`，取法理类型落在 `ai.taxonomy.ENABLED_TYPES` 内的合同；文件名以 `边界样本-` 开头的归为人工构造（`is_manual=True`、id 前缀 `manual_`），其余为真实采集（id 前缀 `batch2_`）；
3. 正文处理：`deidentify(strip_meta(text))` —— `strip_meta` 丢弃所有以 `>` 开头的元信息行（含「法理类型」答案行），`deidentify` 做个人敏感信息脱敏。

> **重要细节**：因为对第一批也额外执行了 `deidentify()`，`classification_test.json` 中第一批的正文**与 `realtest.json` 并非逐字节相同**（多数记录含脱敏标记）。这正是「分类评测」与「风险/要素评测」不能互相替代的原因之一。

| 真实已签署政府采购合同 | **32** | 公开采购渠道（其中 1 份实为公告附件全文，严格计为 31 份政采 + 1 份公告附件） |

### 3.2 类型分布（实测）

买卖合同 19、物业服务合同 11、技术合同 10、建设工程合同 9、租赁合同 9、无名合同 7、承揽合同 6、委托合同 5、劳动合同 4、中介合同 2、保密协议 2 —— 合计 **84**。

### 3.3 ⚠️ 必须如实说明：47 份公开披露合同的「补全风险条款」是**构造数据**

- **实测**：47 份公告披露版合同**全部**含有一节 `## 补全风险条款（按行业惯例构造，用于风险检测评估）`；32 份政采合同与 5 份人工构造合同**均无**该节。
- 该节内容是**按行业惯例/官方范本构造并标注「补全」的条款，不是公告原文**。构造的风险条款是典型风险（违约金过高、无限责任、管辖不利、自动续约等），目的是让风险召回**可测**。
- **因此本报告与本文档必须写明这一点，避免被误读为「这些合同的这些风险都是真实存在的」。**
- 相关的 Gold 标签中，有相当比例的描述文本直接引用了「补全」条款（约 146 条中 115 条描述含「补全」字样，其中 52 条以 `补全风险条款：` 开头）。

**关于「缺失型」的准确表述**：

> 47 份公开披露合同中**被构造的补全风险条款属于构造数据**；但并非这些 Gold 全部是「缺失型」风险 —— 缺失型（R08 + R09）合计 **53 条**，其余约 95 条是显式命中型风险（违约金过高、无限责任、管辖不利、IP 无偿归属、竞业过宽、自动续约、数据共享无边界等）。

### 3.4 记录字段

```jsonc
{
  "id": "realtest_001",
  "source_file": "05_合同\\现实合同\\…\\xxx.md",
  "source": "上市公司公告披露版（…）/ 真实已签署政府采购合同（…）/ 人工构造（…）",
  "true_type": "买卖合同",
  "business_tag": "业务层级标签",
  "elements": {
    "parties":            { "present": true, "raw": "…", "value": "甲方—乙方" },
    "amount":             { "present": true, "raw": "…", "value": "…" },
    "performance_period": { "present": true, "raw": "…", "value": "…" },
    "dispute_resolution": { "present": true, "raw": "…", "value": "…" }
  },
  "risks": [ { "risk_type": "R01", "desc": "条款要点 + 为什么是风险" } ],
  "business_risks": [ "不进严格 F1 的提示项" ],
  "content": "合同全文",
  "gold_source": "pilot_double_annotated"
}
```

- `elements.*.present` 表示该要素在可见文本中**是否被披露**。**只有 `present == true` 的字段才进入要素评测的分母**（见 [`评测方法.md`](./评测方法.md)）。
- `business_risks` 是**纯字符串列表**（不是 `{risk_type, desc}` 结构），共 83 条、分布在 68 份合同中；它们是**提示项，不进严格 F1**。

## 六、Gold 建立方式（如实说明，不夸大）

### 6.1 实际流程

1. **主标**：由一名组员（借助 LLM 辅助）对全量 84 份做首轮标注；
2. **独立复标**：第二名组员对**第 3 批 10 份**在不知首轮结果的前提下**独立盲标**，双方互换比对，得到 4 处风险级分歧；
3. **事后比对**：第 7 批（10 份）、第 8 批（14 份）采用的是「一方落库后，另一方对照比对」的方式，共发现 7 处分歧/漏标；
4. **回溯核查**：其余 **50 份**（第 1/2/4/5/6 批）**没有第二人的独立盲标**，只有事后的回溯核查修正；
5. **分歧仲裁**：所有分歧项与规则性争议按标注口径（规则 A/B/C，见 [`风险标注与Gold规范.md`](./风险标注与Gold规范.md)）逐条定标后写回 Gold。

### 6.2 能够报告与不能报告的一致性指标

**能够报告**：

- 定稿 Gold 的数量与分布（84 份 / 152 条 / 无重复 `risk_type`）；
- 过程本身：主标 → 第 3 批真盲标 → 第 7/8 批事后比对 → 其余批次回溯核查 → 分歧仲裁；
- **复核一致率（合同级）**：第 3 + 7 + 8 批合计 34 份中，27 份完全一致、7 份存在分歧/漏标 → **79.4%**；
- 分歧定标记录（真盲标 4 处 + 规则性争议 7 处 + 回溯修正若干）。

**不能报告**（否则不诚实）：

- **全量 84 份的 Cohen's κ / 互判 macro-F1 / micro-F1** —— 因为其中约 50 份**没有第二人的独立盲标**，硬算出来的分母与分子都是虚的，属「伪双人一致性」。

> 因此本文档与 [`风险标注与Gold规范.md`](./风险标注与Gold规范.md) 统一采用**「双人交叉复核 + 分歧仲裁」**的表述，并给出上面可核查的复核一致率；**不宣称全量 κ**。这是刻意的方法学克制，也是本项目在评测透明度上的实际做法。

`backend/evaluate/deidentify.py` 对第二批分类样本做脱敏，**只移除个人敏感信息、保留分类语义**：

| 去除 | 替换为 |
|---|---|
| 法定代表人 / 法定代理人姓名 | `已脱敏` |
| 手机号（`1[3-9]\d{9}`） | `1**********` |
| 身份证号（18 位） | `******************` |
| 政府采购合同编号前缀（`CSCG/XSCG/GXCG/LYCG/…`） | `[合同编号]` |

**保留**：公司名、项目名、合同标题、标的名称、条款正文。

> 保留公司名与标的是刻意的：删掉会破坏分类器赖以判断的语义特征，从而把分类任务变得不可解。脱敏只针对个人身份信息。

## 八、数据泄漏排查（三道闸）

### 闸 1：去答案元信息

`build_classification_test.py` 的 `strip_meta` 丢弃正文中所有以 `>` 开头的行（含「法理类型」等答案标注），只喂标题 + 正文。

### 闸 2：检索库与正式测试集不同源

RAG 分类器的检索库 `contract_templates` 来自**合同范本样本集**（`03_数据集/测试集/testset.json`，363 条范本），而正式分类测试集 `classification_test.json` 是**真实合同**。两者**不同源**，避免「检索库里就有答案」。

`evaluate_rag.py` 在设计上支持在检索库缺失时回退到范本集路径，该回退路径**仅作冒烟/回归参考，不作为正式泛化指标**。

### 闸 3：评测语料隔离闸（`services/eval_isolation.py`）

对三份官方评测语料的正文做**归一化（去掉所有空白字符）后 sha256** 构成「评测样本指纹集」；经验入库前，用待入库合同正文做同样归一化并比对，**命中即拒绝进入学习**。

这是与「官方评测路径不启用 Feedback RAG」并列的**第二道防线**（defense in depth）：即使有人误开 `FEEDBACK_RAG_ENABLED`，测试样本也无法沉淀成经验。

三份语料：`realtest.json`（84）、`classification_test.json`（147）、`03_数据集/测试集/testset.json`（363）。语料缺失时只告警跳过，不阻断，但会记录**实际检查了哪些来源**。

### 补充：官方评测路径与 Feedback RAG 的隔离（已验证）

`run_evidence.py` 调用的是 `extract_evidence(full_text)` —— 签名**不含** `feedback_context`，函数文档明确标注「签名与行为保持冻结（不暴露 feedback_context），确保官方评测路径无法被注入」。因此**即使开关打开，官方评测 prompt 也逐字节不变**，有回归测试 `test_feedback_rag.py::test_eval_entry_ignores_enabled_flag` 断言这一点。

## 九、评测结果留痕的实际情况（如实说明）

| 指标 | 留痕情况 |
|---|---|
| 风险 P/R/F1（76.6 / 80.1 / 78.3，TP121/FP37/FN30） | **留痕最完整**：与实测 Gold 自洽（121 + 30 = 151 ✓），在项目内多处独立复算一致。 |
| 要素 93.7%（双方 100.0 / 金额 87.2 / 期限 90.8 / 争议解决 96.3） | 文档口径一致；仓库内**没有**该次运行的机器可读结果文件。 |
| 分类 98.6%（145/147） | **仓库内的预测快照 `rag_predictions.json` 记录的是 146/147（99.32%）**。正式口径按既定原则**冻结在 98.6%（145/147）**，不因单次运行到 146/147 而改写（分类 temperature=0.1，结果存在 145↔147 的轻微波动）。 |

> **冻结原则**：正式指标一经确定即冻结，内部重跑出现更高结果**不替换正式口径**；同时如实披露波动范围与留痕情况。
