# 数据集说明

> 描述本仓库评测数据的来源、构建、划分、Gold 建立、脱敏与泄漏排查。数据文件均在 `backend/evaluate/`。

---

## 一、数据集总览

| 文件 | 内容 | 用途 |
|---|---|---|
| `classification_test.json` | **147 份**分类正式测试集（Gold 冻结） | 分类评测 |
| `realtest.json` | **84 份**真实合同（正文 + 分类/elements/risks 标注） | 风险 / 要素评测 |
| `evidence.json` | 84 份的 LLM 证据抽取结果（`run_evidence.py` 产物，可复跑） | 风险评测输入 |

---

## 二、数据来源（真实采集，非生成）

### 2.1 84 份风险/要素测试集（`realtest.json`）

| 来源 | 份数 | 说明 |
|---|---|---|
| 真实已签署政府采购合同 | 32 | 公开采购渠道 |
| 上市公司公告披露版合同 | 47 | 公告披露核心条款 + 按行业惯例/官方范本补全风险条款 |
| 人工构造 | 5 | 4 劳动合同 + 1 保密协议（补齐类目覆盖） |
| **合计** | **84** | 11 类法理全覆盖 |

类型分布：买卖 19、物业 11、技术 10、租赁 9、建设工程 9、无名 7、承揽 6、委托 5、劳动 4、中介 2、保密 2。

### 2.2 147 份分类正式测试集（`classification_test.json`）

| 构成 | 份数 | 说明 |
|---|---|---|
| 第一批 | 84 | 原 `realtest.json`（32 政采 + 47 公告 + 5 人工构造） |
| 第二批 | 55 | 新增真实合同（政采 35 + 公告 20），11 类全覆盖 |
| 人工构造困难边界样本 | 8 | 「边界样本-*」：标题/表面特征误导、跨类特征，专测分类辨别力 |
| **合计** | **147** | = 84 + 55 + 8 |

---

## 三、哪些数据参与哪套评测（关键边界）

| 评测 | 使用测试集 | 份数 |
|---|---|---|
| 分类 | `classification_test.json` | **147**（含第二批 55 + 8 边界） |
| 要素 | `realtest.json` | **84** |
| 风险 | `realtest.json` + `evidence.json` | **84** |

> ⚠️ **第二批 55 份 + 8 个人工构造困难边界样本只进入分类评测，不进入风险/要素评测**；风险 P/R/F1 与要素 F1 仍基于 84 份原测试集。

---

## 四、人工构造样本的用途（如实说明）

- 84 份中的 5 份人工构造（4 劳动合同 + 1 保密协议）用于**补齐类目覆盖**（劳动合同/保密协议在真实公告中样本少）。
- 147 份中的 8 个「边界样本-*」为**困难边界样本**：故意用标题/表面特征误导（如标题写"采购合同"但实质是技术开发）、或携带跨类特征，专门检验分类器在易混类上的辨别力。
- **8 个边界样本显式标记为人工构造（`is_manual`），不伪装成真实自然采集数据**；其余 55 份第二批均为真实采集合同。

---

## 五、Gold 建立方式（避免主观）

1. **背对背独立标注**：组员只依据标注规范（[`风险标注与Gold规范.md`](./风险标注与Gold规范.md)）+ 合同正文判断，互不参考、不参考规则引擎/LLM 输出。
2. **裁定流程**：分歧点经组员人工复核，结合法条与司法解释定标后写回 gold（定标以人工复核为准，不把模型/引擎输出作为 Gold 判定来源）。
3. **一致性保障**：抽批双人标注，用 Cohen's Kappa（主指标）或互当金标准算 F1（目标 Kappa≥0.6 或 F1≥0.7）；拿不准的标「待议」。
4. **风险 gold 规模**：84 份共 **152 条**风险标注（`{risk_type, desc}`，desc 含可定位条款要点）。

---

## 六、脱敏（第二批分类样本）

`evaluate/deidentify.py` 对第二批分类样本做脱敏，**只移除个人敏感信息、保留分类语义**：

| 去除 | 保留 |
|---|---|
| 法定代表人姓名、手机号、身份证号、合同编号 | 公司名 / 项目名 / 合同标题 / 标的名称 / 正文 |

具体规则：法定代表人姓名→「已脱敏」、手机号→「1**********」、身份证号→掩码、合同编号→「[合同编号]」。保留公司名/项目名/标的/正文是为了不破坏分类器的语义判断。

---

## 七、数据泄漏排查

1. **去答案元信息**：分类评测前把「法理类型」等答案元信息从正文剥离，只喂标题 + 正文（`build_classification_test.py` 的 `strip_meta`）。
2. **检索库与正式测试集不同源**：RAG 分类器的检索库 `contract_templates` 来自范本样本集（`03_数据集/测试集/testset.json`），与正式分类测试集 `classification_test.json`（真实合同）**不同源**，避免「检索库里就有答案」的泄漏。
   - 注：`evaluate_rag.py` 的 fallback 路径会退回 `testset.json`（与检索库同源），但脚本明确标注「仅作冒烟/回归参考，不作为正式泛化指标」。
3. **脱敏**：第二批样本先脱敏再进正式测试集，避免个人身份信息进入评测与仓库。

## 八、字段结构

### `realtest.json`（84 份，顶层 list）

```json
{
  "id": "realtest_001",
  "source_file": "…",
  "source": "来源说明（真实签署 / 公告披露 + 公告 URL）",
  "true_type": "买卖合同",
  "business_tag": "业务层级标签",
  "elements": {
    "parties":          { "present": true, "raw": "…", "value": "甲方—乙方" },
    "amount":           { "present": true, "raw": "…", "value": "…" },
    "performance_period":{ "present": true, "raw": "…", "value": "…" },
    "dispute_resolution":{ "present": true, "raw": "…", "value": "…" }
  },
  "risks": [ { "risk_type": "R01", "desc": "条款要点 + 为什么是风险" } ],
  "business_risks": ["不进严格 F1 的提示项"],
  "content": "合同全文",
  "gold_source": "double_annotated"
}
```

### `classification_test.json`（147 份，顶层 list）

每条含 `id`、`true_type`、`content`（已去答案元信息 + 脱敏）、以及人工构造样本的 `is_manual` 标记。
