## 三、`.env` 配置

在**项目根目录**创建 `.env`（模板见 `.env.example`）：

```ini
# DeepSeek API Key（可留空：留空后由各用户在「个人信息」页配置自己的 Key；
# 两者都没有时后端仍可启动，但第一次需要 DeepSeek 的操作会返回明确提示）
DEEPSEEK_API_KEY=

# 数据库：默认部署用 SQLite
DATABASE_URL=sqlite:///./contract.db

# 必填：JWT 签名密钥，必须是非占位随机串
SECRET_KEY=请生成随机长字符串

# 允许的前端来源，逗号分隔
CORS_ORIGINS=http://localhost:5173

# 可选：一次性产生第一个管理员
BOOTSTRAP_ADMIN_USERNAME=

# 可选：Feedback RAG（默认关闭）
# FEEDBACK_RAG_ENABLED=false
```

### 关键约束

1. **`SECRET_KEY` 是必填项**：为空或等于占位串 `change-me-to-random-string` 时，`config.py` 会直接 `raise RuntimeError`（防止弱密钥导致 JWT 在 `--reload` / 多 worker 下失效）。生成方法：

   ```bash
   python -c "import secrets;print(secrets.token_urlsafe(32))"
   ```

2. **不要把真实 Key 提交到 Git**：`.env` 已被 `.gitignore` 忽略，仓库只保留 Key 项留空的 `.env.example` 模板。若曾误提交真实 Key，请立即到 DeepSeek 平台**撤销并重新生成**。
3. `DIFY_API_KEY` / `DIFY_BASE_URL` 是**历史遗留的死配置**（Dify 已从代码中移除），**没有任何代码读取它们**，无需填写、不影响运行。
4. 切换 MySQL：把 `DATABASE_URL` 改为 `mysql+pymysql://user:pass@host:3306/contract_audit`。模型层已做方言对齐（时间统一为应用层写入的 naive UTC；含一段 SQLite 外键列类型迁移）。**注意：SQLite 的 `busy_timeout` 与 WAL 设置仅在 SQLite 下生效。**
5. `DATABASE_URL` 使用相对路径 `./contract.db` 时，数据库文件位置取决于**启动时的工作目录**。内部启动器 `scripts/start_backend.bat` 会先 `cd /d "<项目根>\backend"`，因此实际文件是 `backend/contract.db`。

### DeepSeek Key 的两种来源与优先级

```text
系统默认 Key：.env → DEEPSEEK_API_KEY            （部署方配置，供未配个人 Key 的用户共用）
用户个人 Key：前端「个人信息」→ DeepSeek API Key  （用户自己配置，只作用于该账号）
优先级：      个人 Key  >  系统默认 Key
删除个人 Key：自动回退 系统默认 Key
```

- 部署方的 `DEEPSEEK_API_KEY` **可以留空** —— 留空时由各用户在「个人信息」页配置自己的 Key；
- 两者都没有时，需要 LLM 的操作返回明确提示（HTTP 400）：

  > 「未配置可用的 DeepSeek API Key：请在「个人信息」页配置你自己的 DeepSeek API Key，或联系部署管理员在 .env 中配置系统默认 Key（DEEPSEEK_API_KEY）。」

- **缺 Key 的报错在「调用期」而不是「import 期」**：`ai/llm_client.py` 刻意不做 import 期硬校验，否则「`.env` 不配系统 Key、由每个用户各自配个人 Key」这种部署方式将无法启动；
- **存储**：个人 Key 以 **Fernet**（AES-128-CBC + HMAC-SHA256，密钥由 `SECRET_KEY` 经 SHA-256 派生）加密后存入 `users.deepseek_api_key_enc`，**不是明文**；任何接口只返回 `deepseek_key_configured: true/false`，**任何角色（含 admin）都拿不到 Key 本身**；
- **局限（如实说明）**：安全性等价于 `SECRET_KEY` 的保管强度 —— 拿到 `SECRET_KEY` 即可解密。**轮换 `SECRET_KEY` 会使已存个人 Key 解不开**，此时按「未配置」处理并自动回退系统默认 Key（不会崩溃）；
- **并发隔离**：Key 按请求上下文解析（`ai/llm_context.py` 的 ContextVar，由 `main.py` 的 HTTP 中间件绑定），`DeepSeekClient` 不保存 `api_key`，并**按 Key 哈希缓存** OpenAI client。因此 A 用户的请求永远用 A 的 Key，B 用 B 的，不会串用。

### 首次部署：产生第一个管理员（可选，一次性）

公开注册**只能**得到 `uploader`，其余角色只能由管理员在「用户管理」页分配；而全新库里没有管理员、也就无人可分配，因此提供这个**可选的一次性**开关。

```ini
BOOTSTRAP_ADMIN_USERNAME=      # 填一个【已经注册好】的用户名
```

**正确顺序**（该账号必须已存在，否则不会生效）：

1. 先启动后端，在前端注册一个普通账号（角色为 `uploader`）；
2. 把该用户名填进 `.env` 的 `BOOTSTRAP_ADMIN_USERNAME`；
3. 重启后端 —— 启动时完成提升；
4. 用它登录，在「用户管理」页分配其余账号的角色；
5. 之后不再需要这项配置（留着或删掉都可以）。

**实际行为**（以 `services/role_bootstrap.py` 实现为准）：

| 情况 | 结果 |
|---|---|
| 未配置 / 留空 | 完全跳过（默认行为） |
| 系统里**已有** admin | 完全跳过，**不改动任何角色** |
| 填的用户名**不存在** | 跳过并告警，**不会自动创建账号** |
| 系统里**没有** admin 且该账号存在 | 把**这一个账号**提升为 `admin` |

补充约束：

- **不创建新账号、不改任何密码、不批量修改其他用户** —— 整个过程只写这一个账号的 `role` 字段；
- 每次启动都会检查，但**只有「系统里没有任何 admin」时才会改动**。因此初始化完成后即使配置一直留着，也不会把事后被降权的管理员「复活」；
- 角色分配本身有两条保护：管理员**不能修改自己的角色**；系统**必须至少保留 1 个 admin**。

### Feedback RAG（默认关闭，可选）

```ini
FEEDBACK_RAG_ENABLED=false     # 默认值
```

开启后，**生产审核链路**在证据抽取阶段会检索「已由人工批准且状态为 active 的历史经验」并作为「应重点核查什么」注入 LLM prompt。

**严格边界**（以代码行为为准）：

- 只影响 `extract_evidence_detailed` 的 prompt，**不进入** `rule_engine` / `adjudicate_risks`（裁决仍完全由 Python 决定）；
- **官方评测路径不受影响**：`evaluate/run_evidence.py` 调用的 `extract_evidence(full_text)` 签名不含 `feedback_context`，prompt **逐字节不变**；
- 检索或注入失败只降级为「不使用历史经验」，绝不导致主审核失败。

**完整闭环**（与开关配套的实际链路）：

```
用户审核结果 → 用户反馈/标注（POST /api/feedback）→ feedback_logs 留痕（pending）
→ reviewer 审核（reviewed / rejected）→ admin 批准 → feedback_experiences 风险经验沉淀（active）
→ 独立 feedback RAG 向量集合 → 后续审核混合检索（稠密 + BM25 → RRF）
→ 注入证据抽取 prompt → learning_context 留痕 → 可撤销并从 RAG 精确回退
```

**四条必须说明的边界**：① **不是模型参数微调**（不训练、不更新模型权重，也不修改 R01–R13 规则）；② 属于**基于人工反馈经验的 RAG 辅助优化**；③ **风险最终裁决仍由 `ai/auditor/evidence_adjudicator.py` 的确定性 adjudicator 完成**；④ 开关**默认 `false`**，只有显式开启后才参与生产审核（且仅 `precise` 模式）。

**当前数据现状（如实说明）**：`feedback_logs = 0`、`feedback_experiences = 0`（正式库实测）。即**功能链路已实现并经过测试，但当前尚无真实用户反馈数据沉淀**。

> **载体区分**：`ai/knowledge/risk_cases.json`（Chroma 集合 `risk_cases`）是**预留的规则知识库占位**（当前 0 条，与人工反馈无关）；人工反馈经验的实际沉淀载体是 `feedback_experiences`（表 + 同名 Chroma 集合）。

## 四、启动行为（静启动 / warmup）

启动时 `lifespan` 会依次完成：建表 → SQLite 列迁移 → **复位遗留的 `auditing` 状态** → 一次性 bootstrap 管理员 → **启动后台静启动预热**。

**静启动**（`services/warmup.py`）：进程启动后在**后台 daemon 线程**里提前加载 `torch` / `sentence-transformers` / `chromadb` 与向量库，**不阻塞启动、用户无感知**，避免把冷启动成本（分段实测约 9.2 秒，其中 import 占 7.4 秒）推到「第一次上传合同」上。

进度可**被动查询**：`GET /api/health` → `warmup` 字段：

```json
{ "status": "ok",
  "warmup": { "rag": "ready", "ocr": "idle", "rag_seconds": 8.1, "ocr_seconds": null } }
```

`rag` / `ocr` 取值：`idle` / `warming` / `ready` / `failed`（OCR 另有 `unavailable`）。

| 环境变量 | 作用 |
|---|---|
| `DISABLE_WARMUP=1` | 关闭静启动（单测 / CI 用，避免无谓拖入 torch） |
| `WARMUP_OCR=1` | 额外预热 OCR 引擎（RapidOCR；模型随 wheel 自带、**不联网下载**，默认关闭） |
| `WARMUP_STRICT=1` | 预热异常时抛出（默认只告警，不影响服务） |

预热失败**绝不影响服务**：只记 warning，真正的首次使用仍会照常惰性加载并重试。

## 七、OCR（图片 / 扫描件合同）

- 引擎：**RapidOCR 3.9.2 + ONNX Runtime 1.23.2（单引擎，已不再使用 PaddleOCR / PaddlePaddle）**，入口统一在 `ai/parser/ocr_engine.py`，由 `ai/parser/ocr_parser.py` 适配成与 `parse_pdf` / `parse_docx` 同形的结果；**惰性初始化**（首次用到才实例化），失败则 OCR 不可用；
- **模型随 RapidOCR wheel 自带**（`rapidocr/models/`：PP-OCRv6 det/rec small + 方向分类），因此**不需要联网下载 OCR 模型**，也不需要 Docker / poppler / ImageMagick / ghostscript；
- 扫描 PDF 的栅格化走 `pdfplumber.page.to_image()`（底层 **pypdfium2**，已随 pdfplumber 安装），默认 150 DPI，单份最多 OCR **50 页**（超出截断并记录）；
- 触发路径：`POST /api/contracts/upload`——图片扩展名 `jpg/jpeg/png/tiff/tif/bmp` 直接走 OCR；`.pdf` **先**按原 `parse_pdf` 取文字层，**取不到文字时才**转 OCR（扫描件），普通文字 PDF 不经过 OCR；`.docx` 永远不经过 OCR；
- **质量闸门在解析阶段**（`ocr_engine.assess_quality`，阈值：`MIN_VALID_CHARS = 10`、`MIN_MEAN_CONFIDENCE = 0.75`、`MAX_LOW_CONF_RATIO = 0.5`、低置信判定 `LOW_CONF_THRESHOLD = 0.6`）。命中任一条即判 `ocr_quality="low"` 并直接返回 **422**（同时清理落盘文件）：
  - 无识别结果 → 拒绝；
  - 平均置信度过低（< 0.75）→ 拒绝；
  - 低置信结果比例过高（> 50%）→ 拒绝；
  - 有效字符过少（< 10 字）→ 拒绝。
  只有 `ocr_quality="normal"` 的文本才会进入后续**分类 / 要素抽取 / 风险审核**；
- 输入 → 输出闭环：扫描 PDF / 图片与 DOCX、普通 PDF 一样，可**审核 → 修改 → 导出修订版 DOCX**（由 `parsed_text` 重建中间 DOCX 后再应用修改）。

---

## 八、DOCX→PDF（用于「查看合同原文」）

`services/docx_converter.py::docx_to_pdf()` 的优先级：

1. **Word COM**（`pywin32`）：`win32com.client.Dispatch('Word.Application')` → `SaveAs(FileFormat=17)`；
2. **LibreOffice CLI**：`soffice --headless --convert-to pdf`（`timeout=60s`；会搜索常见安装路径与注册表）；
3. 两者都失败 → `RuntimeError`。

- 有 PDF 缓存（PDF 的 mtime ≥ docx 时复用）；
- 调用点：`GET /api/contracts/{id}/file`，当原文件为 `.docx` 时实时转 PDF 供前端 pdf.js 渲染（完整审核报告页加载较慢即由此而来）；**转换失败会降级返回原 `.docx`**（前端会提示「原文文件无法按 PDF 渲染」）；
- `pywin32` 是**可选依赖**（import 失败自动降级 LibreOffice）。

## 九、启动

### 方式 A：Windows 本地（`prepare.bat` → `start.bat`）

```bat
:: 第 1 步（首次部署只跑一次）：准备 embedding 模型 + 向量库 + 真实校验 RAG
prepare.bat
prepare.bat --rebuild      :: 需要强制重建向量库时

:: 第 2 步（之后每次启动）：唯一对外启动入口，双击即可
start.bat

:: start.bat 只做「检查 -> 启动 -> 报错」，它会：
::   检查 项目结构 / .env 与 SECRET_KEY / RAG 资源 / Python / Node 与前后端依赖
::   然后分别调用下面两个【内部启动器】并各开一个窗口：
::     scripts\start_backend.bat    后端：http://localhost:8080/docs
::     scripts\start_frontend.bat   前端：http://localhost:5173
:: 内部启动器不是独立启动方式，直接运行会提示「请通过项目根目录的 start.bat 启动」。

:: 方式 B：Docker 部署
::   docker compose up -d           （api + web 两个服务，无独立 Chroma 容器）
```

**为什么准备与启动要分开**：`start.bat` 的职责被严格限定为「检查 → 启动 → 报错」，
不做任何安装/下载/重建，否则"一键启动"会变成不可预期的安装器（首次启动耗时数分钟、
失败原因难以定位）。模型下载与向量库构建这类一次性重活统一放在 `prepare.bat`。

`prepare.bat` 的内部步骤与失败处理：

| 步骤 | 做什么 | 失败时 |
|---|---|---|
| 1 | `scripts/prepare_model.py`：模型缺失则下载到 `models/hf-cache`（先官方端点、失败改国内镜像） | 中止并打印三种替代方案（离线完整包 / 手工拷入 / ModelScope） |
| 2 | `backend/chroma_data` 缺失或 `--rebuild` 时，用 `backend/ai/rag/resources/contract_templates_source.json` 重建 | 中止并提示检查建库源与磁盘空间 |
| 3 | `scripts/check_rag_ready.py`：真实加载模型 + 真实检索 + 真实生产分类 | 中止；**不允许**在未就绪时启动 |

> 第 3 步的判定标准是**行为**而不是**目录存在**：要求
> `contract_templates / laws / standard_clauses` 三个集合非空、真实检索命中，
> 且生产分类返回 `method=rag` 与 `fallback=false`。
> 因为 RAG 资源缺失时检索只返回空列表并打 warning，分类会**静默**退化为
> `rag-fallback-llm`（接口仍 200），只看目录是查不出来的。

### 交付包双轨

| 轨道 | 打包脚本 | 是否含模型与向量库 | 体积 |
|---|---|---|---|
| 校赛邮件提交 | `scripts/build_school_package.ps1` | 否（故首次须先跑 `prepare.bat`） | 约 3.6MB，脚本硬校验 ≤50MB |
| 省赛网评 / 现场答辩 | `scripts/build_offline_package.ps1` | 是（解压即离线可用） | 约 435MB |

校赛通知规定电子稿压缩包**总数据量不超过 50MB**，而模型（390MB）+ 向量库（45MB）
远超该上限，因此两个大资源不能进校赛包；省赛参赛指南**没有**总包体积上限
（仅 S4B 演示视频限 150MB），故离线完整包可带全资源。

### 三个交付资源的 Git / LFS / ZIP 策略（实际检查后定案）

| 资源 | 体积 | Git 跟踪 | Git LFS | 校赛小包 | 离线完整包 | 依据 |
|---|---|---|---|---|---|---|
| `backend/ai/rag/resources/contract_templates_source.json` | 7.36 MB | **是** | 否 | 带 | 带 | 建库**源**，不是派生物：没有它 `init_chroma` 就建不起向量库（旧实现指向仓库外路径，只拿到仓库时会静默失效）。7.36MB 单文件在 Git 中完全可接受，无需引入 LFS。 |
| `backend/chroma_data/` | 45.45 MB | 否（`.gitignore`） | 否 | 不带 | 带 | **派生物**：可由上面的建库源用 `prepare.bat --rebuild` 完整重建，因此不必进版本库；二进制且含 17 个文件，进 Git 会永久膨胀每次 clone。 |
| `models/hf-cache/` | 390.27 MB | 否（`.gitignore`） | 否 | 不带 | 带 | 第三方模型权重（`shibing624/text2vec-base-chinese`），可下载、可替换，且体积最大。**不用 LFS** 的理由：LFS 要求拿到仓库的人先装 git-lfs，而比赛交付用的是 ZIP 而不是 clone；同时会让仓库历史持续膨胀。 |

**为什么不用 Git LFS**（本机 `git-lfs 3.7.1` 已安装、`C:` 尚有 162.5 GB 可用，所以不是"装不上"）：
本项目的交付方式是**压缩包**，不是 `git clone`；LFS 只解决"仓库里的二进制文件"问题，
而这两个大资源在本项目里**本就不该进版本库**（一个是派生物、一个是可下载的第三方权重）。
引入 LFS 只会要求评委/队员额外安装 git-lfs，却不带来任何交付收益。

**由此得到的规则**：
- **Git 仓库**保存「源码 + 建库源 + 启动器 + Docker 文件 + 文档」；
- **校赛小包（≤50MB）**保存上述全部，但**不含**模型与向量库 → 首次须先跑 `prepare.bat`；
- **离线完整包**在小包基础上**追加**模型与向量库 → 解压后直接 `start.bat`，无需联网下载模型、
  也无需重新构建向量库。

> ⚠️ 注意：因为两个大资源被 `.gitignore` 忽略，**不要用 `git archive` 打交付包**
> （它只会打包已跟踪内容，会漏掉 `backend/chroma_data/` 与 `models/`）。
> 必须用本文上面的两个打包脚本，它们按文件系统复制并逐项校验。

### 等价的手动启动

```bat
:: 后端（等价于 scripts\start_backend.bat）
cd backend
venv\Scripts\python.exe -m uvicorn main:app --reload --host 0.0.0.0 --port 8080
```

### 6. 评测数据是如何构建与质检的（简述）

三套评测使用**已定稿的冻结数据集**；数据本身的构建过程不在本机复现（原始材料与脚本在仓库外的工作区），此处只作如实说明：

```
公开合同材料 → 候选采集 → 公告 / 完整合同筛选 → 必要时合同正文还原（PDF 文本层 / 网页全文转写 / 扫描件 OCR / 公告→披露版整理）
→ 双人独立背对背标注 → 第三人审计 → 分歧复核 → 最终人工裁决 → 正式评测数据 / Gold
```

- 公开来源中存在大量**合同公告、采购公告、成交公告、结果公告、合同签订公告**类材料，**不等同于完整合同正文**，因此先由人工筛选；**无法可靠还原为合同正文的材料不纳入**正式评测集，**不为了扩大数据量而强行纳入**；
- 标注由**两名标注人员独立阅读、互不查看对方结果**完成，再由**审计人员**检查证据是否来自原文、标签是否符合定义、是否存在明显冲突，分歧经复核后按既定规则最终裁决；
- **只有第 3 批 10 份是真正的双人独立盲标**，因此项目统一表述为「**双人交叉复核 + 分歧仲裁**」，只报告可核查的**合同级复核一致率 79.4%**，**不宣称全量 κ**；
- 该结果是**项目人工参考标准**，不是外部权威金标准；**不以模型预测作为 Gold 依据，也不为提升指标修改 Gold**。

完整流程见 [`评测方法.md`](./评测方法.md) 第九节与 [`数据集说明.md`](./数据集说明.md) 第六节。

## 十二、常见问题

| 问题 | 处理 |
|---|---|
| 启动报 `必须配置 SECRET_KEY` | `.env` 的 `SECRET_KEY` 为空或仍是占位串，改为随机长字符串 |
| 调用 LLM 报「未配置可用的 DeepSeek API Key」 | 在「个人信息」页配置个人 Key，或在 `.env` 配置 `DEEPSEEK_API_KEY`。**这是调用期报错，不影响后端启动** |
| 第一次上传合同很慢 | 静启动预热尚未完成（可查 `/api/health` 的 `warmup`）；预热完成后第一次上传明显变快 |
| 图片 / 扫描件上传返回 422 | OCR 引擎不可用、或**质量闸门未通过**（无识别结果 / 平均置信度 < 0.75 / 低置信占比 > 50% / 有效字数 < 10）→ 换更清晰的原件重新上传 |
| DOCX 原文预览失败 | 未装 Word 或 LibreOffice；两者都无时后端会降级返回原 `.docx`，前端提示「无法按 PDF 渲染」 |
| 前端请求被 CORS 拦截 | `utils/request.js` 用绝对地址直连 8080，必须在 `.env` 的 `CORS_ORIGINS` 里加入前端实际来源 |
| 分类结果在 145/146/147 之间波动 | temperature=0.1 的正常波动；**正式口径冻结在 98.6%（145/147）** |
| 修订版 DOCX 下载返回 400 | 见 [`条款修改与修订机制.md`](./条款修改与修订机制.md) 第 5.2 节的前置换条件；最常见原因是「有修订尚未建立可靠原文定位」。**注意：非 DOCX（PDF / 图片）同样可以导出修订版**，它们由 `parsed_text` 重建中间 DOCX 后再应用修改 |
| 并发审核出现 `database is locked` | SQLite 单写者限制。已用 WAL + `busy_timeout=30s` + 缩短写事务窗口缓解；**高并发场景应切 MySQL**（非默认） |
