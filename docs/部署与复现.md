## 三、`.env` 配置

在**项目根目录**创建 `.env`（模板见 `.env.example`）：

```ini
# 必填：DeepSeek API Key（缺失会导致后端 import 即失败）
DEEPSEEK_API_KEY=sk-你的key

# 数据库：开发用 SQLite，生产用 MySQL
DATABASE_URL=sqlite:///./contract.db

# 必填：JWT 签名密钥，必须是非占位随机串（填 change-me-to-random-string 会启动失败）
SECRET_KEY=请生成随机长字符串

# 允许的前端来源，逗号分隔
CORS_ORIGINS=http://localhost:5173
```

> ⚠️ 注意：
> 1. `SECRET_KEY` 为空或等于占位串 `change-me-to-random-string` 时，`config.py` 会直接 `raise RuntimeError`（防止弱密钥）。生成方法：`python -c "import secrets;print(secrets.token_urlsafe(32))"`。
> 2. `config.py` 默认 `DATABASE_URL` 是 MySQL；开发用 `.env` 覆盖为 SQLite。切 MySQL 时把 `DATABASE_URL` 改为 `mysql+pymysql://user:pass@host:3306/contract_audit`。
> 3. `DIFY_API_KEY`/`DIFY_BASE_URL` 是历史遗留的死配置（Dify 已删除），无需填写、不影响运行。

## 四、LLM 配置

- 模型：`deepseek-chat`（DeepSeek 官方 API）
- 接口：`https://api.deepseek.com`（OpenAI 兼容，`backend/ai/llm_client.py` 硬编码）
- API Key：环境变量 `DEEPSEEK_API_KEY`（**必填**，import 时即校验）
- 超时/重试：单次调用 `timeout=30s`、`max_retries=0`；重试由各调用方自行实现（如建议层重试 1 次）
- temperature（按模块）：分类/条款比对/改条款 = 0.1；要素/证据/建议 = 0.0

## 五、RAG 配置

- **向量库**：ChromaDB 持久化，目录 `backend/chroma_data`（`anonymized_telemetry=False`）
- **Embedding**：`sentence-transformers` 的 `shibing624/text2vec-base-chinese`（`max_seq_length=512`）
- **集合**：`laws`（法条库）、`standard_clauses`（标准条款）、`risk_cases`（预留）、`contract_templates`（范本分类库，用于 RAG 少样本分类）
- **检索**：`search_knowledge()` 为混合检索（Chroma 稠密 + BM25 稀疏 → RRF 融合）；`search_similar_templates()` 用于分类器取 top-K 相似范本
- **离线模式**：启动即设 `HF_HUB_OFFLINE=1`、`TRANSFORMERS_OFFLINE=1`，首次需联网下载 embedding 模型到本地缓存
- **初始化建库**（首次运行）：

```bash
cd backend
python -m ai.rag.init_chroma
```

> 懒加载：应用启动不主动加载向量库/embedding，首次检索时才加载，避免拖慢启动。

## 六、OCR 依赖（图片/扫描件合同）

- 引擎：**PaddleOCR**（`lang="ch"`），由 `backend/ai/parser/ocr_parser.py` 使用
- **惰性初始化**：首次上传图片才 import/实例化，失败则 OCR 不可用（返回 error），不阻塞其他格式
- PaddlePaddle ≥3.3 时显式 `enable_mkldnn=False`（规避 PIR→oneDNN bug）
- 置信度阈值 0.6；低置信占比 >30% 判 `ocr_quality="low"`
- 触发路径：`POST /api/contracts/upload` 保存文件后，按扩展名 `jpg/jpeg/png/tiff/tif/bmp` 同步调用 OCR；空文本/失败返回 422 并清理落盘文件

> 若不需要处理图片/扫描件，可不安 PaddleOCR/PaddlePaddle（体积大），不影响 docx/pdf 审核。

## 七、DOCX→PDF 依赖（前端预览）

`backend/services/docx_converter.py` 的 `docx_to_pdf()` 优先级：

1. **Word COM（pywin32）**：`win32com.client.Dispatch('Word.Application')` → `SaveAs(FileFormat=17)`（PDF）
2. **LibreOffice CLI**：`soffice --headless --convert-to pdf`（`timeout=60s`）
3. 两者都失败 → `RuntimeError`

- 有 PDF 缓存（PDF mtime ≥ docx 时复用）
- 调用点：`GET /api/contracts/{id}/file`，当原文件为 `.docx` 时实时转 PDF 供前端 pdf.js 渲染；转换失败降级返回原 .docx
- pywin32 是**可选依赖**（import 失败自动降级 LibreOffice）

## 十、三套评测与当前正式指标复现

工作目录 `backend/`，`python` 用已装依赖的解释器。

### 1. 分类（147 份正式测试集）

```bash
python evaluate/evaluate_rag.py
```

- 输入：`evaluate/classification_test.json`（147 份，Gold 冻结，正文已去答案元信息）
- 输出准确率 + 每类 P/R/F1 + 预测快照 `evaluate/rag_predictions.json`
- **正式口径：98.6%（145/147）**

### 2. 要素抽取（84 份）

```bash
python evaluate/evaluate_elements.py
```

- 输入：`evaluate/realtest.json`（84 份），结果按 md5 缓存于 `evaluate/cache_elements.json`
- 输出四要素逐项 P/R/F1 + 披露样本加权综合 F1
- **正式口径：93.7%（双方 100.0 / 金额 87.2 / 期限 90.8 / 争议解决 96.3）**

### 3. 风险识别（84 份，证据+裁决）

```bash
python evaluate/run_evidence.py        # 预计算 LLM 证据 → evidence.json（有缓存可跳过）
python evaluate/evaluate_evidence.py
```

- 输入：`evaluate/realtest.json` + `evaluate/evidence.json`；裁决走生产 v6.4 `adjudicate_risks`（R01–R12）
- 输出 TP/FP/FN + P/R/F1
- **正式口径：P 76.6% / R 80.1% / F1 78.3%（TP 121 / FP 37 / FN 30）**

> 三套评测均走 DeepSeek `deepseek-chat`，分类 temperature=0.1（存在 145↔147 轻微波动，正式口径冻结在 98.6%）。详见 [`评测方法.md`](./评测方法.md)。

## 十一、常见问题

| 问题 | 处理 |
|---|---|
| 启动报 `必须配置 SECRET_KEY` | `.env` 里 `SECRET_KEY` 为空或占位串，改成随机长字符串 |
| 启动报 `DEEPSEEK_API_KEY` 错误 | `.env` 里配置真实 DeepSeek key |
| 上传 docx 预览失败 | 未装 Word/LibreOffice；pywin32 缺失会自动降级 LibreOffice，两者都无则返回原 docx |
| 上传图片 OCR 很慢/失败 | 首次会下载 PaddleOCR 模型；未装 paddle 则 OCR 不可用 |
| 分类结果 145/146/147 波动 | temperature=0.1 的正常波动，正式口径冻结 98.6%（145/147） |
