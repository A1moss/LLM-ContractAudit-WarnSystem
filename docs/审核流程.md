# 审核流程

> 入口：`POST /api/contracts/{id}/audit` → 后台任务 `backend/api/contracts.py::_run_audit`
> 审核模式：`precise`（默认，规则 + 证据裁决 + 建议）/ `fast`（纯规则引擎初筛）
> 本文所有步骤、阈值、降级分支均以代码为准。

---

## 一、流程总览

```
合同上传
  │
  ├─ 1. 文件解析 / OCR       ai/parser/                    → parsed_text
  │      docx_parser / pdf_parser / ocr_parser
  │
  ├─ 2. 文本清洗与分块        ai/chunker.py                 → 按条款标题边界分块
  │
  ├─ 3. 合同类型分类          ai/classifier/rag_classifier.py → contract_type + is_outsourcing
  │      RAG 少样本（检索 top-K 范本作示例 → LLM 判定）；无检索结果时降级零样本
  │
  ├─ 4. 合同要素抽取          ai/extractor/extractor.py      → extracted_elements
  │      双方 / 金额 / 签订日期 / 履行期限 / 争议解决 / 适用法律
  │
  ├─ 5. 规则召回（基线）      ai/auditor/rule_engine.py      → R01–R13 确定性正则 + 缺失型规则
  │
  ├─ 6. 风险证据提取（LLM）   ai/auditor/evidence_extractor.py → 结构化事实证据（不下结论）
  │
  ├─ 7. Python 确定性裁决     ai/auditor/evidence_adjudicator.py → R01–R12 风险对象
  │
  ├─ 8. 法律依据 / 修改建议   ai/auditor/recommendation_engine.py → 风险说明 / 建议 / 示例 / 法条
  │
  ├─ 9. 条款比对             ai/matcher/matcher.py          → 覆盖率 / 缺失 / 偏离 / 跨条款风险
  │
  ├─ 10. 置信度融合           ai/confidence.py               → 交叉验证上调
  │
  ├─ 11. 条款定位 + 入库       _locate_clause → AuditRecord
  │
  └─ 12. 审核报告             contracts.py → AuditReport（风险表 + 条款比对章节）
```

**第 1–4 步在上传时完成**（`POST /contracts/upload`，分类与要素抽取并行执行）；**第 5–12 步在触发审核时由后台任务完成**。

## 二、上传阶段（第 1–4 步）

### 1. 文件解析 / OCR —— `ai/parser/`

| 格式 | 解析器 | 说明 |
|---|---|---|
| `.docx` | `docx_parser.py`（python-docx） | 逐段落提取，标记 `is_heading`；**不经过 OCR** |
| `.pdf`（有文字层） | `pdf_parser.py`（pdfplumber） | 逐页提取文字层，保留页号；**行为未变、不触发 OCR** |
| `.pdf`（无有效文字层 = 扫描件） | `scan_pdf.py` → `ocr_parser.py` | 逐页栅格化（`page.to_image()`，底层 pypdfium2，150 DPI）后走 **RapidOCR**；单份最多 50 页，超出截断并记录 |
| `.jpg/.jpeg/.png/.tiff/.tif/.bmp` | `ocr_parser.py`（**RapidOCR 3.9.2 + ONNX Runtime 1.23.2**） | 单引擎、模型随 wheel 自带（无需联网下载）；惰性初始化；输出按页 + 阅读行排序（确定性） |

`detect_and_parse()` 按扩展名分发：`.pdf` **先**走原 `parse_pdf`，只有确实取不到文字时才转 OCR（普通文字 PDF 因此完全不走 OCR）。上传端点接受的上传格式白名单与之一致。

**OCR 质量闸门（在解析阶段完成，未通过不进入后续分类 / 要素抽取 / 审核）** —— `ocr_engine.assess_quality`：

| 判据 | 阈值 | 结果 |
|---|---|---|
| 无识别结果 | 框数 = 0 | 拒绝（`ocr_quality = "low"`） |
| 平均置信度过低 | `MIN_MEAN_CONFIDENCE = 0.75` | 拒绝 |
| 低置信结果比例过高 | `MAX_LOW_CONF_RATIO = 0.5`（单条低置信判定 `LOW_CONF_THRESHOLD = 0.6`） | 拒绝 |
| 有效字符过少 | `MIN_VALID_CHARS = 10` | 拒绝 |

通过则 `ocr_quality = "normal"`，文本写入 `contracts.parsed_text` 再进入第 2 步。**闸门发生在上传/解析阶段**，被拒绝的请求不会留下合同记录与落盘文件。

**空文本处理（显式分支，不静默产生空合同）：**

| 情况 | 响应 |
|---|---|
| 扩展名不在白名单 | 400 `仅支持 pdf/docx 或图片格式(jpg/png/tiff/bmp)` |
| 解析抛异常 | 422 `parse failed: …`，并删除已落盘文件 |
| **图片 / 扫描 PDF**：OCR 引擎不可用、无识别结果、或质量闸门未通过 | 422 `OCR 识别质量过低，请上传更清晰的合同图片/扫描件。（<原因>）`，原因取自引擎或质量评估，例如「RapidOCR 未正确安装或初始化失败」「OCR 未识别到任何文字」「OCR 平均置信度过低（0.62）」「OCR 低置信结果过多（80%）」「OCR 有效文字过少（仅 6 字）」「扫描件未识别到任何文字」「扫描件页面栅格化失败：…」 |
| 防御性历史分支（当前解析器不再产生，代码保留） | 422 `文本提取失败：<原因>`（需解析器给出 `error`，当前 `parse_pdf` / `parse_docx` 不产生）、`图片未识别到文字，请确认图片清晰或上传 PDF/DOCX 格式`（需图片解析不给 `ocr_quality`，当前 `parse_image` 总会给）、`未能从文件中提取到文字（可能是扫描版 PDF 无文字层）…`（该文案现作为上一条的「原因」出现） |

### 2. 文本清洗与分块 —— `ai/chunker.py`

`split_chunks(text, max_chars)`：优先在**条款标题行**断块（`第X条` / `第X章` / `第X款` / `一、` / `（一）` / `1.`），保证条款完整性；单段超长时在换行处硬切；无编号的纯段落退化为按行硬切。

各环节的单块上限（`max_chars`）：

| 环节 | 上限 | 备注 |
|---|---|---|
| 证据抽取 | 20000 | `evidence_extractor.MAX_CHARS` |
| 条款比对 | 6000 | `matcher.MAX_COMPARE_CHARS` |
| 要素抽取 | 4000 | `extractor.MAX_EXTRACT_CHARS` |
| 零样本分类（回退路径） | 4000 | `classifier.MAX_CLASSIFY_CHARS`，最多采样 5 块投票 |

分块的意义是**长合同尾部不漏检**——早期只读开头固定字数会漏掉位于合同后半的违约责任/争议解决条款。

### 3. 合同类型分类 —— `ai/classifier/`

生产默认走 **RAG 少样本分类**（`ai/classifier/__init__.py` 把 `rag_classifier.classify_by_rag` 导出为 `classify_contract`）：

1. 用 `search_similar_templates(full_text[:12000], top_k+1)` 在「合同范本分类库」检索最相似的 K 篇**已分类范本**；
2. 把范本的首 600 字 + 尾 300 字作为「参考示例」连同类型一起喂给 LLM；
3. LLM 输出 `{contract_type, is_outsourcing, confidence, reason}`。

**回退路径**：检索无结果 → 调用 `ai/classifier/classifier.py::classify_contract`（纯 LLM 零样本，分块采样最多 5 块投票聚合）。

**两个独立判断**（务必区分）：

- `contract_type`：**法理分类**，11 类单一互斥（8 典型 + 2 无名 + 1 特别法），唯一真源 `ai/taxonomy.py`；
- `is_outsourcing`：**业务标签**（布尔，可叠加），「服务外包」不是法理分类——一个合同法理上可以是承揽/技术/委托，业务上同时是服务外包。劳务派遣**不是**服务外包。

实测准确率 **98.6%（145/147）**，详见 [`评测方法.md`](./评测方法.md)。

### 4. 合同要素抽取 —— `ai/extractor/extractor.py`

LLM 抽取六个字段：`parties`（归一化到甲方/乙方）、`amount`（value/currency/text）、`sign_date`、`performance_period`（start/end）、`dispute_resolution`、`governing_law`。分块并行后按「**空不覆盖非空**」逐字段合并。

要素抽取与分类在**上传时并行执行**（`ThreadPoolExecutor` + `submit_with_context`，保证工作线程能读到用户个人 Key）。

**注意：要素抽取对 `contract_type` 不敏感**，因此上传时用中性词占位、不等分类结果，以缩短等待。

## 三、审核阶段（第 5–12 步，`_run_audit`）

### 5. 规则召回（基线）—— `ai/auditor/rule_engine.py`

`RISK_RULES` 定义 **R01–R13 共 13 条**规则，两类实现：

- **正则命中型**（R01–R07、R10–R12）：`re.finditer` 命中后取上下文 ±30 字；有 `SAFE_PATTERNS` 白名单过滤（如「违约金不超过20%」不判 R01）；有 `_is_negated()` 否定语境过滤（R13 用）。
- **缺失型**（R08、R09）：全文不含「验收」相关词 → R08；全文不含「不可抗力」→ R09。
- **信号组合型**（R13）：`NAME_REALITY_SIGNALS` 的「名义信号 + 实质信号」任一组合同时命中即示警。

**规则引擎始终先跑**：既是 `fast` 模式的全部内容，也是 `precise` 模式异常时的降级兜底。

### 6. 风险证据提取（LLM，只抽事实）—— `ai/auditor/evidence_extractor.py`

这是本系统技术边界的核心环节。LLM 的 system prompt 明确：

> 「唯一任务：从合同原文中**只抽取客观事实**，**绝对不要判断是否构成风险、不要下法律结论、不要输出 risk/is_risk 字段**。」

抽取字段（12 组，与 R01–R12 一一对应）：

`R01_违约金` / `R02_责任` / `R03_单方权利`（termination·suspension·change 三子项）/ `R04_管辖` / `R05_保密` / `R06_IP` / `R07_付款` / `R08_验收` / `R09_不可抗力` / `R10_竞业` / `R11_续约` / `R12_数据`，另加 `contract_type`、`is_delivery_type`。

工程实现要点：

- **正文与「补全风险条款」分段抽取**：`_split_supplement()` 按 `## 补全风险条款` 切分，两段各自分块并行，再用 `_merge_override()` 做字段级覆盖（中性值「无/未写明/固定期限」不覆盖正文，避免误杀）；
- **失败语义显式区分**：`_extract_chunk` 返回 `None` = 失败，返回 `{}` = 成功但该块无风险事实。二者不再混用；
- **状态信封**：`extract_evidence_detailed()` 返回 `{evidence, status, failed_chunks, total_chunks}`，`status ∈ {success, partial, failed}`；
- 失败块不计入证据但计入 `failed_chunks`，**成功块结果全部保留**（一块失败不丢弃其它块结果）。

**降级规则（`_run_audit` 中的显式分支）：**

| `status` | 行为 |
|---|---|
| `success` | 正常裁决 |
| `partial` | 保留成功块证据继续裁决，记 warning |
| `failed` | 记 error，**整体降级为规则引擎粗筛结果**，绝不伪装成 0 风险 |

### 7. Python 确定性裁决 —— `ai/auditor/evidence_adjudicator.py`

`adjudicate_risks(evidence)` 按硬阈值裁决 **R01–R12**，输出完整风险对象。阈值见 [`风险规则说明.md`](./风险规则说明.md)。

要点：

- **R13 不在本层**：R13 只由规则引擎产出（`evidence_adjudicator` 的 `RISK_NAMES`/`LEVELS`/`SUGGESTIONS` 均只定义 R01–R12）；
- **数值归一化** `_num()`：字符串百分比/千分号自动换算（`"5%"→0.05`、`"5‰"→0.005`），避免 LLM 输出字符串被静默跳过；
- **同义归一化**：`_normalize_scope()`（R10 的「全国/全球/境内/不限地域」统一为「全国」）、`_normalize_mode()`（R11 中英文「沉默自动续约」统一）；
- **去重**：按 `(risk_type, clause_text[:40])` 去重；
- **裁决为空且抽取成功 = 如实报 0 风险**，绝不回退规则引擎（避免把规则误报当结论）。

### 8. 法律依据 / 修改建议 —— `ai/auditor/recommendation_engine.py`

只消费裁决结果，**不反向影响** `risk_type` / `level`：

1. **法条检索**：按 `RULE_LAWS[risk_type]` 里的法条编号在 `ai/knowledge/laws.json`（161 条）**精确取条文**，不做向量语义检索（避免 R11→无固定期限、R12→技术秘密这类语义漂移）；取不到时只返回法条编号引用；
2. **LLM 生成**：批量一次调用（temperature=0.0，超时重试一次），每条输出 `risk_description` / `suggestion` / `example`，受 `RISK_GUARDRAILS` 的 `direction` + `forbidden` 约束；
3. **按索引回填 + 类型校验**：LLM 返回顺序不一致或类型不匹配时回退模板兜底；空建议/空说明回退到 guardrail 方向；
4. **接地检查** `recommendation_grounding_check()`：建议中出现的阿拉伯数字/比例、中文数字必须能在 `evidence` / `legal_basis` / RAG 检索内容中找到来源，否则记入 `issues` 并写入 `grounding = {passed, issues}`（前端据此显示「该建议含未经证据核实的数值」警告）。

### 9. 条款比对 —— `ai/matcher/matcher.py`

`compare_clauses(full_text, contract_type, is_outsourcing, standard_clauses)`：

- **结构过滤**（参考 PAKTON 的结构化检索思想）：按合同类型从 `standard_clauses.json`（257 条，11 个类型）取对应条款，**而不是**拿类型名去做语义检索；
- **企业模板优先**：若 `templates` 表里该合同类型有最新版本，则使用企业自定义模板（`_db_template_clauses`）；`is_outsourcing=True` 时额外叠加「服务外包」补充条款集；
- **分块并行比对**（上限 6000 字/块），合并时同一标准条款取**覆盖状态最优**的一条（covered > partial > missing）；
- 输出 `{clauses, summary{total, covered, partial, missing, coverage_rate}, missing_critical, cross_clause_risks}`；
- **跨条款图分析** `_cross_clause_risks()`：利用标准条款库的 `depends_on`（前置依赖）与 `conflict_with`（互斥冲突）字段检测两类**单条比对发现不了**的联动风险——「前置依赖缺失」与「条款互斥冲突」。

**执行时机与失败处理：**

- 本条**在 DB 写事务之前执行**（LLM 耗时约 30s；若放进写事务会长时间持有 SQLite 写锁，导致并发审核 `database is locked`）；
- 比对失败**不阻断审核**，报告中该章节标注 `⚠️ 条款比对未完成（知识库未初始化或比对失败），可稍后重试`。

`coverage_rate = covered / total`。

### 10. 置信度融合 —— `ai/confidence.py`

- 按来源补基础置信度：`detection_method == "rule"` → 查 `RULE_CONFIDENCE` 表（R01 0.90 / R02 0.92 / R08·R09 0.72 …，默认 0.80）；语义来源未给出时用中性 `0.60`；
- 按 `(risk_type, clause_text[:30])` 聚类，同一风险被多来源独立检出时交叉验证上调（2 来源 +0.07，≥3 来源 +0.12，上限 0.95/0.98）；
- 全部结果夹到 `[0.05, 0.99]`。

> 说明：当前生产链路的 `detection_method` 只有 `rule` 与 `evidence` 两种，因此 +0.12 分支实际不会触发；代码保留它是为了兼容历史上的多来源检测。

### 11. 条款定位 + 入库

- **定位** `_locate_clause(full_text, clause_text)`：用条款文本前缀逐级缩短（30→20→10→6→4 字）在 `parsed_text` 中查找，容忍 LLM 证据对原文的改写；多命中时用「（N）子项」消歧（`_pick_best_hit`），无法唯一消歧则返回 `-1`（显式定位失败，不随便取第一个）；命中后 `_locate_at()` 截取子条款窗口（边界为（N）子项/句号/分号/换行，上限 150 字，超限回退 ±60 字），并从最后一个「第X条」标题解析真实条号；
- 结果写入 `audit_records.clause_position`（`{clause_no, clause_title, original_text, start, end}`）。**`original_text` 就是后续 DOCX 导出使用的逐字原文锚点**；
- **批次与状态**：重新审核时旧的 `valid` 记录置 `superseded`（不物理删除，保留审计轨迹）；`audit_batch` 为本次批次 UUID。

### 12. 审核报告

- 风险计数 `high / medium / low`；
- **风险评分** `risk_score = min(100, high×30 + medium×15 + low×5)`；
- `report_html`（风险表 + 条款比对章节，所有动态字段 `html.escape` 防存储型 XSS）；
- `risk_heatmap_data`（高/中/低计数）、`missing_clauses`（条款比对完整结果，前端「条款完整性」直接读它）；
- 写入 `AuditReport`，`contracts.status = "completed"`；
- 以上与记录插入**同处一个事务**，中途异常统一 rollback。

## 四、两个审核模式

| 模式 | `audit_mode` | 实际执行 | 用途 |
|---|---|---|---|
| **精细审核** | `precise`（**默认**） | 第 5–12 步全量（规则 + 证据抽取 + 确定性裁决 + 建议层 + 条款比对） | 主口径 |
| **快速初筛** | `fast` | **只有第 5 步**（规则引擎） | 确定性基线，秒级出结果 |

后端 `Contract.audit_mode` 默认 `"precise"`，上传端点 `audit_mode: str = Form("precise")`，前端展示为「精细审核（推荐）」/「快速初筛」。

> 历史教训（代码注释中保留）：默认 `fast` 会输出纯规则的粗糙结果，因此默认值在三处统一为 `precise`。

## 五、上传 → 审核 → 复核 → 验收 → 修改 的完整时序

```
① uploader 上传合同           POST /contracts/upload        → status=parsed
② uploader/reviewer/approver 触发审核
                              POST /contracts/{id}/audit     → status=auditing（原子占位，重复提交 409）
                              后台 _run_audit 执行第 5–12 步  → status=completed
③ reviewer 复核
                              POST /contracts/{id}/review?action=approve → status=reviewed（待验收）
                              POST /contracts/{id}/review?action=reject  → status=parsed，当前有效记录置 rejected
④ approver 验收               POST /contracts/{id}/approve   → status=approved
⑤ 任何可见角色发起条款修改     POST /contracts/{id}/revise    → 写 ClauseRevision
⑥ 确认采用某一版              POST /contracts/{id}/revisions/{rid}/adopt → adopted=True
⑦ 下载修订版 DOCX             GET  /contracts/{id}/revised-docx
```

**职责分离硬约束**：reviewer **不得复核自己上传的**合同，approver **不得验收自己上传的**合同（代码直接 403）。

## 六、涉及的关键 API

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/contracts/upload` | 上传 + 解析 + 分类 + 要素抽取（限 uploader/admin） |
| POST | `/api/contracts/{id}/audit` | 触发审核（后台任务） |
| POST | `/api/contracts/{id}/review` | 复核通过 / 驳回（reviewer） |
| POST | `/api/contracts/{id}/approve` | 验收（approver） |
| GET | `/api/contracts/{id}/audit-result` | 当前批次的风险记录 + 建议层 + 证据（含 `has_current_result`） |
| GET | `/api/contracts/{id}/audit-report` | 报告统计 + `report_html` + 条款比对结果 |

完整 API 清单见 [`系统功能说明.md`](./系统功能说明.md) 的「API 一览」。

## 七、设计经验（数据验证过的取舍）

1. **LLM 的布尔/数值输出稳定，复杂枚举与多层嵌套数组容易崩** → 因此结构化程度高的判定交给代码，LLM 只输出扁平事实字段。
2. **关键词匹配优于让 LLM 做二分类** → R02 无限责任用 `scope`/`absolute_text` 关键词匹配，不用 LLM 分类。
3. **建议层必须防编造** → grounding 检查 + prompt 明令示例中不写具体数字。
4. **RAG 按编号精确取条文，不做语义检索** → 避免语义漂移。
5. **失败必须显式可见** → 块失败、比对失败、定位失败都是显式状态/日志，不静默降级成「看起来正常」。
