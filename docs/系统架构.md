# 系统架构

> 本文描述**当前仓库实际实现**的架构。所有模块名、文件名、字段名均以代码为准。
> 凡代码中已删除、已归档或未接入生产链路的组件，在文末「已废弃与不存在的组件」一节中明确列出，**不作为当前架构描述**。

---

## 一、项目定位

**A24 · 基于大模型的企业合同智能审核与风险预警系统**（命题企业：网新恒天）

面向企业法务与风控部门，覆盖「合同上传 → 解析/OCR → 分类 → 要素抽取 → 风险识别 → 修改建议 → 条款比对 → 审核报告 → 条款修改 → 修订版 DOCX 导出」的完整闭环。

系统的核心主张是**人机协同**：机器负责可重复的证据提取与确定性判定，人负责最终定性、位置确认与版本采纳。

## 二、一条不可动摇的技术边界

> **LLM 负责理解、抽取证据、生成建议；Python 负责最终风险裁决。**

这不是文档上的修辞，而是代码中的结构性约束：

| 环节 | 承担者 | 代码位置 | 是否允许 LLM 下风险结论 |
|---|---|---|---|
| 合同类型分类 | LLM + RAG 少样本 | `ai/classifier/rag_classifier.py` | 是（这是分类，不是风险裁决） |
| 要素抽取 | LLM | `ai/extractor/extractor.py` | 否（只抽事实） |
| **风险事实证据抽取** | **LLM，只抽客观事实** | `ai/auditor/evidence_extractor.py` | **明确禁止**（prompt 明令不得输出 `risk`/`is_risk` 字段） |
| **风险裁决** | **纯 Python 硬阈值** | `ai/auditor/evidence_adjudicator.py` | — |
| 风险说明 / 修改建议 | LLM + grounding 校验 | `ai/auditor/recommendation_engine.py` | 否（不改变 `risk_type` / `level`） |
| 条款比对 | LLM 比对 + Python 图分析 | `ai/matcher/matcher.py` | 否（比对结果不是 R01–R13 风险） |
| 条款修订 / 新增起草 | LLM | `ai/reviser.py` | 否（返回文本，不改风险结论） |

因此，本系统**不是**「把合同丢给大模型让它判断有没有风险」。正确表述是：

> 大模型把合同条款翻译成结构化事实证据，Python 按固定阈值裁决这些事实是否构成 R01–R12 风险。

`ai/auditor/evidence_extractor.py` 的 system prompt 是这条边界的直接体现：

> 「唯一任务：从合同原文中**只抽取客观事实**，**绝对不要判断是否构成风险、不要下法律结论、不要输出 risk/is_risk 字段**。」

## 五、核心审核链路（`precise` 精细审核）

入口 `POST /api/contracts/{id}/audit` → BackgroundTasks 执行 `api/contracts.py::_run_audit()`：

```
1. 规则引擎基线        run_rules(full_text)                  ai/auditor/rule_engine.py
   R01–R13 正则 / 缺失型规则，始终先跑，作为 fast 基线与降级兜底

2. 证据抽取（LLM）     extract_evidence_detailed(full_text)  ai/auditor/evidence_extractor.py
   · 按条款标题边界分块（MAX_CHARS=20000），多块并行
   · 正文与「## 补全风险条款」段各自分块并行，补全段做字段级覆盖
   · 只抽事实，禁止输出风险结论
   · 返回状态信封 {evidence, status(success|partial|failed), failed_chunks, total_chunks}

3. 确定性裁决（Python） adjudicate_risks(evidence)           ai/auditor/evidence_adjudicator.py
   按硬阈值裁决 R01–R12，输出完整风险对象
   （risk_type / level / name / clause_text / reason / suggestion /
     detection_method="evidence" / confidence / related_law）

4. 建议层（LLM）       build_recommendations(risks, evidence) ai/auditor/recommendation_engine.py
   · 按 RULE_LAWS 法条编号在 laws.json 精确取条文
   · 生成风险说明 / 修改建议 / 修改示例
   · recommendation_grounding_check() 拦截无来源的数字与比例
   · 只增加展示字段，绝不修改 risk_type / level

5. 条款比对            compare_clauses(...)                   ai/matcher/matcher.py
   · 结构过滤（按合同类型取标准条款）+ 分块并行 LLM 比对
   · 输出 clauses / summary / missing_critical / cross_clause_risks
   · 在写事务之前执行（LLM 耗时长，避免长时间持有 SQLite 写锁）

6. 置信度融合          enrich_confidences(all_risks)           ai/confidence.py

7. 落库（单事务）      _mark_audit_records(valid→superseded) + 逐条 AuditRecord
                      + AuditReport + contracts.status = "completed"
```

**降级与失败语义（以下均为代码中的显式分支）：**

| 情况 | 行为 |
|---|---|
| 证据抽取全部块失败（`status == "failed"`） | 记 error 日志，**降级为规则引擎粗筛结果**，不伪装成「0 风险」 |
| 证据抽取部分块失败（`status == "partial"`） | 保留成功块证据继续裁决，并显式 warning |
| 裁决结果为空但抽取成功 | **如实报 0 风险**，不回退规则引擎（避免把规则误报当结论） |
| 裁决抛异常 | 记 error，退回规则引擎结果 |
| 条款比对失败 | 不阻断审核，报告标注「条款比对未完成…可稍后重试」 |
| 后台审核整体异常 | 主事务 rollback + 独立 session best-effort 恢复合同状态为 `parsed`；进程重启时 `lifespan` 复位遗留的 `auditing` |
| `audit_mode == "fast"` | 跳过第 2–4 步，**只跑规则引擎**（快速初筛） |

`audit_mode` 只有 `precise`（默认）与 `fast` 两个取值。

## 六、RAG 体系

### 6.1 四个 Chroma collection

`ai/rag/vector_store.py` 的 `COLLECTIONS`：

| collection | 中文名 | 建库源 | 实际状态 |
|---|---|---|---|
| `laws` | 法律法规库 | `ai/knowledge/laws.json`（**161 条**） | 已建成 |
| `standard_clauses` | 标准条款库 | `ai/knowledge/standard_clauses.json`（**257 条**，覆盖 11 个合同类型） | 已建成 |
| `risk_cases` | 风险案例库 | `ai/knowledge/risk_cases.json` | **空集合（0 条）**，仅预留 |
| `contract_templates` | 合同范本分类库 | `backend/ai/rag/resources/contract_templates_source.json`（范本样本集，363 条） | 供 RAG 分类检索范本 |

### 6.2 混合检索

`search_knowledge()` = **稠密语义检索（ChromaDB + text2vec）+ BM25 词面检索 → RRF 融合**。

- 稠密检索失败（模型未就绪等）自动降级为仅 BM25，不报错；
- 检索结果按 `clause_id` 关联回 JSON 下标空间（不靠 content 反查，避免同文重复条目张冠李戴）；
- 知识库 JSON 缓存按源文件 `(mtime_ns, size)` 版本号失效。

### 6.3 建库源与评测集分离（防泄漏）

- **建库源**：`backend/ai/rag/resources/contract_templates_source.json`（合同范本样本集，363 条，随源码入库）
- **评测集**：`backend/evaluate/classification_test.json`（真实合同）、`backend/evaluate/realtest.json`

模板库建库源是仓库内**独立的范本样本集文件**，不直接使用受保护的评测测试集作为模板库数据源，两者**不同源**，避免「检索库里就有答案」。

> **口径说明（不矛盾，是同一份资源的两种身份）**：`contract_templates_source.json` 与仓库外 `03_数据集/测试集/testset.json` **逐字节同源**（sha256 一致），当初随源码迁入仓库以解决「只拿到仓库时建不起向量库」；同时该文件也被 `services/eval_isolation.py` 登记为**受保护的评测语料**之一。即：它是范本库的**建库源**，同时受隔离闸保护——只是它**不是**分类正式测试集（`classification_test.json`），两者不可混用。

此外还有第二道闸 `services/eval_isolation.py`：对三份官方评测语料正文做归一化 sha256 指纹，与其正文完全一致的合同正文**禁止沉淀为学习经验**。

### 6.4 Feedback RAG（默认关闭）

开关是 `config.py` 的 `FEEDBACK_RAG_ENABLED`，**默认 False**。开启后仅在**生产审核链路的证据抽取阶段**注入「已由人工审核并批准」的历史经验，作为「应重点核查什么」的提示。

结构性边界（不是文案承诺）：

- 只影响 `extract_evidence_detailed` 的 prompt，**不进入** `rule_engine` / `adjudicate_risks`；
- 官方评测路径 `extract_evidence(full_text)` 的签名**不含** `feedback_context`，**无法被注入**；
- 检索或注入失败一律降级为「不使用历史经验」，绝不让主审核失败。

### 6.5 人工反馈 → 风险经验库 → 后续 RAG 的闭环（Human-in-the-Loop）

这是一条**已实现并经过测试**的完整链路，与上节的开关配合使用：

```
用户审核结果
  ↓
用户反馈 / 标注        POST /api/feedback（唯一录入入口，普通用户即可提交）
  ↓                   前端：components/FeedbackPanel.vue（确认 / 修正 / 误报 / 补充 / 撤销）
feedback_logs 留痕     status = pending（谁、何时、对哪条记录、标了什么、写了什么理由）
  ↓
reviewer 审核          POST /api/feedback/{id}/review → reviewed / rejected（不得审核自己提交的）
  ↓
admin 批准             POST /api/feedback/{id}/approve（不得是提交者，也不得是审核者 → 职责分离）
  ↓
feedback_experiences   ★ 风险经验沉淀载体（reviewed → approved_for_learning → active）
  ↓                    构造逻辑：services/feedback_experience.py（静态模板，只写「应重点核查什么」）
独立 feedback RAG 集合  Chroma 集合 feedback_experiences（与 laws / standard_clauses / contract_templates 隔离）
  ↓                    入库/删除：ai/rag/feedback_store.py
后续审核混合检索        稠密（Chroma）+ BM25 → RRF 融合；只加载 status='active'
  ↓
注入证据抽取 prompt     作为【人工历史参考】注入（仅 precise 模式 + 开关开启）
  ↓
learning_context 留痕   audit_records.learning_context（index_version / experience_ids[] / applied_chunks）
  ↓
可撤销并精确回退         POST /api/feedback/{id}/revoke → 按 doc_id 精确删除 Chroma 文档 + status=revoked
```

**四条结构性边界（不是文案承诺）：**

1. **不是模型参数微调**：不训练、不更新任何模型权重，也不修改 R01–R13 规则；
2. 属于**基于人工反馈经验的 RAG 辅助优化**（检索历史经验并注入 prompt），而非让模型"学会"新标签；
3. **风险最终裁决仍由 `ai/auditor/evidence_adjudicator.py` 的确定性 adjudicator 完成**，经验进不了裁决层；
4. 只有 `active` 的经验可被检索；`approved_for_learning`（入索引失败）不会被检索，但经验行保留可重试。

**三道防污染机制**（与本节 6.3 配套，防止评测被反向污染）：

| 机制 | 实现 | 作用 |
|---|---|---|
| 官方评测路径不可注入 | `run_evidence.py → extract_evidence(full_text)` 签名不含 `feedback_context` | 即使开关打开，评测 prompt **逐字节不变** |
| 评测语料隔离闸 | `services/eval_isolation.py`（三份语料归一化 sha256 指纹） | 与评测语料完全一致的合同正文**禁止沉淀为经验** |
| 规则类反馈禁止入库 | `feedback_reason == adjudicator_rule_suspect` 只进规则反馈池 | 规则问题必须人工改规则 + 跑回归，**不自动生效** |

**当前数据现状（如实说明）：`feedback_logs = 0`、`feedback_experiences = 0`（正式库实测）。**
即：**功能链路已实现并经过测试（`test_feedback_experience.py` 22 项 / `test_feedback_rag.py` 29 项），但当前尚无真实用户反馈数据沉淀。**

**载体区分（不得混为一谈）**：

- `risk_cases.json`（Chroma 集合 `risk_cases`）= **预留的规则知识库占位**，当前 **0 条**；
- `feedback_experiences`（表 + 同名 Chroma 集合）= **实际设计中的人工反馈风险经验沉淀载体**（当前 0 条，但链路可用）。

## 七、LLM 出口与密钥管理

全项目**唯一** LLM 出口是 `ai/llm_client.py` 的 `llm_client.chat()`。

**Key 解析优先级：用户个人 Key > `.env` 的 `DEEPSEEK_API_KEY`（系统默认 Key）**

- 请求级绑定在 `main.py` 的 HTTP 中间件 `bind_user_llm_key`（必须放中间件：依赖运行在线程池线程，改不到端点上下文）；
- 绑定通过 `ai/llm_context.py` 的 ContextVar 实现，天然按请求隔离，不存在串 Key；
- `ThreadPoolExecutor` 新线程**不继承** contextvars，因此所有并发提交统一走 `submit_with_context()`；
- 两者都没有 Key 时抛 `LLMConfigError`，API 层转成明确的 400 提示（**绝不发送空 Key**，也不静默降级）；
- 用户个人 Key 由 `services/user_secret.py` 用 Fernet 加密落库（密钥由 `.env` 的 `SECRET_KEY` 经 SHA-256 派生）；任何接口**只返回 `deepseek_key_configured` 布尔值**，不回显 Key 本身或片段。

| `revision_proposals` | `RevisionProposal` | contract_id / user_id / instruction / **status(draft\|partially_applied\|applied)** / summary / items(JSON) / confirmed_ids(JSON) |

**三个字段必须理解清楚：**

- `audit_records.audit_batch`：一次审核批次的 UUID。`audit-result` 只返回**最新批次**，避免并发审核多批次混杂。
- `audit_records.result_status`：`valid` / `rejected` / `superseded`。重新审核时旧的 `valid` 置 `superseded`，驳回时置 `rejected`，**都不物理删除**（保留审计轨迹）。
- `clause_revisions.adopted`：用户是否**明确确认采用**该版本。同一 `(contract_id, clause_key)` 至多一行为 `True`。

`clause_revisions` 上有复合索引 `ix_clause_revisions_contract_key (contract_id, clause_key)`。

## 九、合同状态机（`contracts.status`）

```
uploaded ──解析成功──> parsed ──触发审核──> auditing ──审核完成──> completed
                         ▲                    │                      │
                         │                    │ 失败 / 重启复位        │ reviewer 复核通过
                         │                    └──────────────────────┤
                         │                                           ▼
                         └──── reviewer 驳回 ◄──── completed     reviewed
                                                                     │ approver 验收
                                                                     ▼
                                                                 approved
（任意状态）── 删除 ──> deleted（软删除，文件归档到 data/deleted/）
```

前端展示映射（`constants/reportTokens.js`）：`uploaded 已上传 / parsed 已解析 / auditing 审核中 / completed 审核完成 / reviewed 待验收 / approved 已验收`。

## 十、权限体系（4 个角色，服务端强制）

角色常量在 `api/deps.py`：`ROLE_UPLOADER` / `ROLE_REVIEWER` / `ROLE_APPROVER` / `ROLE_ADMIN`。

**判定权威来源是数据库中的真实角色**（`get_current_user` 每次从库读用户），与 localStorage / JWT 中客户端可控的 role 字段无关。

| 能力 | uploader | reviewer | approver | admin |
|---|---|---|---|---|
| 上传合同（`POST /contracts/upload`） | ✅ | ❌ 403 | ❌ 403 | ✅（`require_role` 恒通过） |
| 查看合同列表 / 详情 | 仅**自己**的 | 公司范围全部 | 公司范围全部 | 全部 |
| 删除合同 | 仅自己的 | ❌ | ❌ | 任意 |
| 触发审核 / 改条款 / 导出修订版 | 自己可见的合同 | 全部可见合同 | 全部可见合同 | 全部 |
| 复核（`/review`） | ❌ | ✅（**不得复核自己上传的**） | ❌ | ✅ |
| 验收（`/approve`） | ❌ | ❌ | ✅（**不得验收自己上传的**） | ✅ |
| 模板新建 / 修改 | ❌ | ✅ | ❌ | ✅ |
| 模板删除 | ❌ | ❌ | ❌ | ✅ |
| 用户列表 / 改角色（`/auth/users`） | ❌ | ❌ | ❌ | ✅ |
| 反馈审核（reviewer）/ 批准（admin） | ❌ | 审核 | ❌ | 批准 |
| 个人信息 / 个人 Key | ✅ | ✅ | ✅ | ✅ |

补充规则（均为代码中的真实约束）：

- **公开注册固定为 `uploader`**：`RegisterRequest` 不接受 `role` 字段，客户端传 `role=admin` 也会被忽略；
- 已删除（`status == "deleted"`）的合同**所有角色一律不可见**；
- 管理员**不得修改自己的角色**，且系统必须**至少保留一名 admin**；
- 第一个管理员通过一次性部署开关 `BOOTSTRAP_ADMIN_USERNAME` 产生：仅当库中**0 个 admin** 且指定账号**已存在**时提升该账号，**绝不自动建号、不改密码**。

## 十一、并发与事务设计要点

| 问题 | 措施 |
|---|---|
| 重复审核 | `UPDATE ... WHERE status != 'auditing'` 原子占位（乐观锁），并发只允许一个请求成功，否则 409 |
| SQLite 写锁竞争 | `busy_timeout=30s` + WAL 模式；LLM 长调用（条款比对）**放在写事务之外** |
| 审核失败残留 `auditing` | 独立 session best-effort 恢复为 `parsed`（退避重试 3 次）；进程启动时再复位一次 |
| 审核中途异常丢数据 | 记录 + 报告 + 状态合并为**一个事务**，异常统一 rollback |
| 并发审核批次混杂 | `audit-result` 只返回最新 `audit_batch` |
| 启动冷启动 | `services/warmup.py` 静启动：daemon 线程后台预热 torch / 向量模型 / 向量库，启动不阻塞；进度可查 `GET /api/health → warmup` |

## 十三、当前架构的真实局限（如实列出）

1. **SQLite 单写者**：并发写能力有限。已用 WAL + `busy_timeout` + 缩短写事务窗口缓解，但这**不是**解决并发写的方案。
2. **证据抽取依赖 LLM 质量**：某块失败只计入 `failed_chunks`，对应条款的风险要素**可能丢失**（系统显式记录，不静默吞掉）。
3. **R05 无 Gold、R13 不入 F1**：风险评测只对 R01–R12 中**实际有 Gold** 的风险计算 P/R/F1（详见 [`评测方法.md`](./评测方法.md)）。
4. **修订版统一输出 DOCX**：DOCX / 普通 PDF / 扫描 PDF / JPG / PNG 都支持导出修订版 DOCX（非 DOCX 输入由 `parsed_text` 重建中间 DOCX 后再应用修改）；**不支持** PDF→PDF 或图片→图片导出，也不支持导出「未修改的原件」。
5. **修订版不生成 Word 修订痕迹（Track Changes）**，也不做完整版本管理。
6. **同一段原文被两个不同会话都确认采用时**，DOCX 归并仍按锚点后写覆盖（已在代码注释中记录的已知边界）。
7. **条款比对质量取决于该合同类型是否有标准条款**；无对应条款时回退到全部条款或提示「没有可用的标准条款范本」。
8. **审核报告导出**：有正式 **PDF** 导出接口（**没有** Word 报告导出）；报告页亦支持浏览器打印。
9. **反馈经验闭环尚无真实数据**：`feedback_logs = 0`、`feedback_experiences = 0`（正式库实测）。链路已实现并经过测试，但尚无真实用户反馈数据沉淀；同时 Feedback RAG **默认关闭**（`FEEDBACK_RAG_ENABLED=False`），开启后也只在 `precise` 模式生效。
10. **`risk_cases.json` 为空**（0 条），风险案例库仅预留占位；它**不是**人工反馈经验的载体（后者是 `feedback_experiences`，见 6.5）。
