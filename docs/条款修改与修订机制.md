# 条款修改与修订机制

> 本文描述**当前实际实现**的合同条款修改系统：两种修改范围、多轮会话、版本历史、「确认采用此版」语义、R09 缺失条款补充、以及修订版 DOCX 导出。
> 涉及代码：`api/contracts.py`（revise / adopt / revised-docx / locate-clause / add-clause-suggestion）、`api/overview.py`（总体会话）、`models/clause_revision.py`、`models/revision_proposal.py`、`services/docx_reviser.py`、`ai/reviser.py`、前端 `views/contract-detail/RevisionWorkbench.vue` 及同目录子组件。

---

## 一、两种修改范围

系统的修改能力分为两个**明确的**范围，二者都落在同一张表 `clause_revisions` 上，通过 `scope` 区分。

### 1. `clause` —— 专项条款修改会话

- 针对**某一个具体对象**：一条 R01–R13 风险条款，或一条条款比对问题（缺失/偏离的标准条款）；
- **支持多轮对话**：每一轮都是一条 `ClauseRevision` 记录，`clause_key` 相同的记录构成一个「会话」；
- 每一轮结果都被保存，可以随时回看任意一轮的修改稿与对比；
- 可以继续调整，也可以「确认采用此版」；
- **可以写进修订版 DOCX**（前提是该轮已建立可靠原文定位；新增条款需已确认插入位置）。

前端会话标识 `clause_key` 的取值规则（`composables/useContractWorkspace.js`）：

| 来源 | `clause_key` |
|---|---|
| 风险来源 | `str(AuditRecord.id)`，如 `"12"` |
| 条款比对来源 | `"__cmp__" + 标准条款标题`，如 `"__cmp__验收标准"` |
| 无 key 的历史脏数据 | `"__orphan__{id}"`（前端归入「历史修改」组） |

### 2. `overview` —— 总体修改会话

**它不是「把整份合同重写一遍覆盖原 DOCX」，也不是纯聊天区。** 它是「修改合同」工作台的总控入口，链路固定为：

```
读取全部专项修改会话
  → 形成综合上下文
  → AI 分析整份合同的修改关系
  → 形成【结构化综合修改方案】（逐项：replace / add_clause）
  → 用户逐项查看与确认
  → 每一项转换成【现有安全的 clause / add_clause 修订】
  → 复用现有定位 + 现有 DOCX 安全导出
```

三条硬约束是**结构性保证**，不是文案承诺：

1. **方案 ≠ 修改**：`POST /overview/plan` 只写 `revision_proposals`（方案表），**不建立任何 `ClauseRevision`**。方案表没有 `original_clause_text` 锚点字段，**不参与也无法参与 DOCX 导出**。
2. **`overview + replace` 永不写 DOCX**：`download_revised_docx` 的取数口径只取 `scope == "clause"`，或 `scope == "overview" AND operation == "add_clause"`。历史上「整体讨论稿」仍只作为讨论记录保存。
3. **不新写第二套系统**：定位复用 `api/contracts.py` 的 `_locate_clause` / `_locate_at` / `_parse_headings` / `_suggest_position`；落库复用与 `POST /{id}/revise` 完全相同的字段与锚点规则；导出复用 `services/docx_reviser`。

前端表现：左栏会话导航的「总体修改」组；中栏输入整体要求；右栏「总控台」(`OverviewPlanPanel.vue`) 展示「当前修改点汇总」与「本轮综合修改方案」，每项可「纳入方案 / 取消纳入 / 跳过 / 去专项会话处理」。

> **实现状态（如实说明）**：前端「纳入方案」会**真实调用** `POST /overview/confirm` 落库（`useContractWorkspace.js` 的 `confirmOverviewItem` → `api/contract.js` 的 `confirmOverviewProposal`），因此"总体会话确认后写库"这条链路在**接口层与当前前端界面**上均已打通；确认后写入的是 `ClauseRevision`（`scope` 等字段与 `POST /{id}/revise` 同规则）。

## 二、数据模型：`clause_revisions`

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | int | 主键，**即时间顺序** |
| `contract_id` | int | 所属合同 |
| `scope` | `clause` \| `overview` | 会话作用域 |
| `operation` | `replace` \| `add_clause` | 替换已有条款 / 新增缺失条款 |
| `position` | JSON \| null | 新增条款插入位置：`{"anchor":"五","hint":"第五条之后"}` 或 `{"append":true,"hint":"追加到合同末尾"}` |
| `clause_key` | str | 会话标识（见上表） |
| `clause_no` | str \| null | 条款编号 |
| `clause_text` | Text | **本轮输入**的条款原文（第一轮 = 风险条款原文；后续轮 = 上一轮修订结果） |
| `original_clause_text` | Text \| null | **真实原文锚点**：审核阶段从合同正文定位到的逐字原文，供 DOCX 精确替换 |
| `instruction` | Text | 用户本轮要求 |
| `revised_clause` | Text | 本轮 AI 修订结果 |
| `explanation` | Text | 一句话修订说明 |
| `constraints` | JSON | Leader 给出的硬性约束 |
| `legal_basis` | JSON | 法律依据 |
| `remaining_risks` | JSON | Self-QA 复核出的剩余风险 |
| **`adopted`** | bool | **用户是否明确确认采用该版本**（默认 False） |
| `created_at` | datetime | 创建时间（naive UTC） |

`(contract_id, clause_key)` 上有复合索引 `ix_clause_revisions_contract_key`（采用确认与 DOCX 归并都按这两个字段过滤）。

## 三、多轮修改会话

### 3.1 后端接口

`POST /api/contracts/{id}/revise`（`ReviseRequest`）：

```jsonc
{
  "clause_text": "当前条款原文",     // operation=replace 必填；add_clause 可不填
  "instruction": "用户的修改要求",   // 必填
  "history": [ {"instruction": "…", "revised_clause": "…"} ],   // 历史轮次（多轮上下文）
  "scope": "clause",                // "clause" | "overview"
  "clause_key": "12",               // 会话标识
  "clause_no": "3",
  "operation": "replace",           // "replace" | "add_clause"
  "position": null                  // add_clause 时的插入位置
}
```

`POST /api/contracts/{id}/revisions/{revision_id}/adopt`（`AdoptRevisionRequest`）：`{ "clause_key": "12" }`

### 3.2 `replace` 路径：Leader-Follower 三步修订

`ai/reviser.py::revise_clause()` 用三次 LLM 调用完成一轮修订（参考 RCBSF 的博弈层级设计）：

| 步骤 | 角色 | 职责 | 输出 |
|---|---|---|---|
| 1 | **Leader（约束设定方）** | 解析用户指令 + 法条 → 给出硬性修订约束，先动、锁定策略空间 | `target` / `constraints` / `legal_basis` / `risk_type` |
| 2 | **Follower（执行方）** | 在 Leader 约束诱导的空间内修订条款原文 | `revised_clause` / `changes` / `explanation` |
| 3 | **Self-QA（终审复核）** | 校验修订是否满足约束、是否引入新风险 | `verified` / `remaining_risks` / `final_advice` |

- `history` 最多取最近 5 轮带入 prompt，实现持续迭代细化；
- RAG 检索到的法条（`search_knowledge(instruction, "laws", 3)`）同时提供给 Leader 与 Follower；
- 任一环节失败或 JSON 解析失败 → 返回 `{"error": …}`，**端点返回 502 且不落库**（不再伪装成 200 成功）。

### 3.3 `add_clause` 路径：单次起草

新增条款是「起草」而不是「修订」，因此**不走 Leader-Follower**，只用一次 LLM 调用（`generate_clause()`）：

- 输入：用户指令 + 合同类型 + RAG 法条 + RAG 同类范本 + 建议插入位置提示；
- 输出：`{clause_text, explanation, legal_basis}`；
- 端点统一把新增正文放进 `revised_clause` 字段返回（与替换型一致，前端与持久化共用）。

### 3.4 原文锚点是如何建立的（DOCX 能导出的前提）

落库前，`replace` 路径按以下**优先级**确定 `original_clause_text`（每一步都是确定性逻辑，不调 LLM）：

1. **审核阶段已保存的锚点**：`scope == "clause"` 且 `clause_key` 是数字时，读取对应 `AuditRecord.clause_position.original_text`；
2. **复用审核同一个定位算法**：若上一步为空（条款比对等非风险来源没有 AuditRecord 锚点），调用 `_locate_clause(parsed_text, clause_text)` 在合同正文中定位；
3. **沿用同会话上一轮的锚点**：多轮续接时本轮 `clause_text` 已是上一轮修订稿、不再出现在原文中，于是取该 `clause_key` 下最近的、`original_clause_text` 非空的记录沿用。

代码注释明确：**不再拿 LLM evidence 去 `parsed_text` 里重新猜位置——原文锚点的权威来源是合同解析文本。**

`add_clause` 路径**不解析锚点**（新条款没有原文），由 `_final_add_clause_map` 单独处理，与 `scope` 无关。

### 3.5 轮次记录与刷新恢复

- `GET /api/contracts/{id}/revisions` 返回该合同**全部**修订会话（按 `id` 升序），含 `adopted` 字段；
- 前端据此把记录按 `clause_key` 分组重建会话与轮次，**刷新页面后仍能恢复**（包括「已采用」标记）；
- 每一轮不做合并、不做删除。

## 四、「确认采用此版」的准确语义

这是当前系统的重要语义，**必须与「生成一轮修改」严格区分**。

### 4.1 状态流转

```
生成修改版本（POST /revise，每成功一轮落一行）
        ↓
默认 adopted = false
        ↓
用户：
  ├── 确认采用此版（POST /revisions/{id}/adopt）
  │       ↓
  │   adopted = true
  │
  └── 继续调整
          ↓
      生成下一版本（仍是 adopted = false）
```

### 4.2 后端行为（`adopt_contract_revision`）

- **不调用 LLM**；
- **不新建 `ClauseRevision`**；
- **不改动轮次**；
- 只把目标行置 `adopted = True`，并把同一 `(contract_id, clause_key)` 下**其它**行的 `adopted` 清掉；
- 「清旧 + 置新」在**同一个事务**里完成，一次 `commit`；
- 返回 `{revision_id, clause_key, adopted, superseded_revision_id, superseded_count}`。

> **不要再写成「点击确认采用会再次调用 LLM 生成版本」——当前不是这个逻辑。**

### 4.3 唯一性范围

**同一 `(contract_id + clause_key)` 只能存在一个最终采用版本。**

### 4.4 采用前置校验（不满足直接 400）

| `operation` | 前置条件 | 不满足时的提示 |
|---|---|---|
| `add_clause` | `position` 可解析：`append == true`，或 `anchor` 能被解析为条款编号 | `该新增条款尚未确认合法插入位置，不能采用` |
| `replace` | `original_clause_text` 非空（已建立可靠原文定位） | `该修订尚未建立可靠原文定位，不能采用` |

另外，查询时**同时带 `contract_id`**，防止拿别的合同的 `revision_id` 来确认；`clause_key` 必须与目标修订一致，否则 400。

### 4.5 前端表现

- 「修改合同」工作台右栏「操作」卡片：**「确认采用此版」**（已采用则禁用并显示 `✓ 已采用`）+ **「继续调整」**；
- 「继续调整」的实际行为是**把光标聚焦到中栏输入框**，不会自动发送任何内容；
- 采用成功后重新拉取 revisions 与 overview 并提示「已采用这一版（下载修改合同时会使用它）」；
- 采用态来自后端 `adopted` 字段，**刷新后仍能恢复**。

### 4.6 新增条款是另一套确认动作

新增条款会话的操作按钮是 **「确认新增」**（`confirmNewClause`），它提交的是**一轮新的 `POST /revise`**（`instruction` 带 `【确认新增】` 前缀），语义与「确认采用此版」不同：前者是「再生成并落库一轮」，后者是「标记某一轮为采用」。

### 4.7 已知边界（代码注释中已记录）

采用态的唯一范围是 `(contract_id, clause_key)`，而 DOCX 最终按 **anchor** 归并；若两个**不同会话**命中**同一段原文**且都被采用，导出时仍会后写覆盖前写。

## 五、DOCX 修订版导出

### 5.1 完整链路

```
审核（定位到逐字原文 → audit_records.clause_position.original_text）
   ↓
风险条款定位（clause_key = str(AuditRecord.id)）
   ↓
修改会话（POST /revise，多轮，每轮落一行 ClauseRevision）
   ↓
确认采用（POST /revisions/{id}/adopt → adopted = True）
   ↓
DOCX 修订版导出（GET /contracts/{id}/revised-docx）
```

### 5.2 端点与前置换条件（`download_revised_docx`）

| 顺序 | 条件 | 失败响应 |
|---|---|---|
| 1 | 合同存在且有权查看 | 404 `contract not found` |
| 2 | 源格式在**可导出白名单**内：`.docx` / `.pdf` / `.jpg` / `.jpeg` / `.png` / `.tiff` / `.tif` / `.bmp` | 400 `当前源文件格式暂不支持导出修订版（已支持 .docx / .pdf / 图片）` |
| 3 | 原文件在磁盘上存在 | 404 `原始合同文件不存在` |
| 4 | 存在可导出记录（`scope=="clause"` 或 `scope=="overview" && operation=="add_clause"`） | 400 `当前合同还没有任何条款修改，无法生成修订版` |
| 5 | **所有**替换型记录中，凡有 `clause_text` 与 `revised_clause` 的，都必须有非空 `original_clause_text` | 400 `有 N 条修订无法在合同原文中定位，未写入修订版；请对该条款重新发起一次修改（保存时会重新定位原文锚点）后再下载` |
| 6 | 新增条款插入位置能在文档中可靠定位 | 400，`detail` 为具体原因（如 `未找到插入位置「五」`） |
| 7 | 实际替换/插入成功数 > 0 | 400 `修订条款未能定位到原文，无法生成修订版` |

**导出策略：优先采用 `adopted=true` 的版本；若该归并组内没有 adopted 版本，则按既有兼容逻辑取最新一条。**

### 5.3 为什么能用真实 DOCX 原文定位

系统**不使用 LLM evidence 当替换锚点**，而是：

1. 审核阶段把从 `parsed_text` 定位到的**逐字原文**存进 `ClauseRevision.original_clause_text`；
2. 导出时用该原文锚点在 DOCX 段落里做定位与**子串替换**。

关键实现（`services/docx_reviser.py`）：

- **段内子串替换 `p.text.find(anchor)`**：找到锚点后只替换该子串，`p.text = 前段 + 修订文本 + 后段`。这避免了「整段替换」造成的正文丢失风险（一个段落里往往有多个句子，整段覆盖会把没改的内容一起洗掉）；
- **多段兜底**：子串未命中时，用 `_find_paragraph_indices()` 三级匹配（① 段落包含条款片段 → 单段；② 条款片段横跨多段 → 多段；③ 最长公共子串 ≥ 15 兜底），命中多个段落时只把修订文本写入第一段、其余置空；
- **不修改原文件**，只另存为 `revised_<uuid>.docx`，下载后由 BackgroundTasks 清理临时文件；
- **不做 Word 修订痕迹（Track Changes）**，也不做完整版本管理。

### 5.4 链式归并与采用态优先（`_final_clause_map`）

连续修改同一条款时（A → A1 → A2），前端第二轮输入的 `clause_text` 是上一轮的 `revised_clause`。系统据此把 A2 归并回原始 A：

- **归并组 = 同一个 anchor**；组内选谁生效由 `_pick_final()` 决定：
  1. 组内**存在** `adopted=True` 的行 → 在这些行里取「最后一条」（`id` 最大）；
  2. 组内**没有任何** adopted → 取整组「最后一条」（**与引入 adopted 之前逐字一致**，保证历史数据零回归）。
- 无 `original_clause_text` 锚点的旧修订**直接跳过**（需要重新发起一次修改以重建锚点）。

### 5.5 新增条款（R09）的插入与最小化编号处理

`_final_add_clause_map()` 先归并：**同一插入位置只保留最终一条**（用户对同一条新增条款多轮修改会产生多条 `add_clause` 记录，位置相同 → 只保留最终版，避免重复插入）。归并组 = `_pos_key(position)`（`"append"` 或 `"anchor:<编号>"`），组内同样**采用态优先**。

插入时按文档结构自动选择三种模式：

| 模式 | 触发条件 | 行为 |
|---|---|---|
| `_append_clause` | `position.append == true` | 追加到文档末尾；编号取文档中最大标题编号 + 1；**无可识别标题时不猜编号**，直接追加正文 |
| `_insert_paragraph_level` | 存在以 anchor 编号开头的**独立段落** | 在 anchor 段落之后、下一标题段落之前插入，并**把编号 > anchor 的所有标题整体 +1** |
| `_insert_inline` | 整份合同落在一个段落内 | 在该段落内联标题处插入，同样**顺延后续编号**；无法可靠识别插入位时返回明确错误 |

**「最小化编号处理」的含义**：系统只做**必要的顺延**——新增条款占用 `anchor + 1` 号，其后所有更大编号统一 +1。它不重排、不重写其它条款正文，不改动标题以外的任何内容。

插入失败（位置无法定位）时**抛 `ValueError`**，端点据此返回 400 并附具体原因。

### 5.6 导出失败即完整失败（不生成残缺文件）

这是刻意的产品选择：**宁可不能导出，也不能导出一份漏改的 DOCX。**

- 端点侧额外统计 `anchorless`（有文本内容但无锚点的替换型记录数）——因为 `_final_clause_map` 对这类记录**连 skipped 都不计**，直接丢弃；
- `anchorless + skipped > 0` → 删除临时文件并返回 400，明确告知有 N 条修订未写入；
- `applied == 0` → 删除临时文件并返回 400；
- 新增条款插入失败 → 删除临时文件并返回 400（`detail` 为具体原因）；
- 其它异常 → 删除临时文件并返回 500 `生成修订版 DOCX 失败，原合同文件可能已损坏`。

### 5.7 前端导出状态机

`composables/workspaceLogic.js::docxStateFor` 有四个状态：

| key | 文案 |
|---|---|
| `not_docx` | 当前合同的修订版暂不支持导出（`detail`：`当前源文件格式（.<ext>）暂不支持导出修订版；已支持 .docx / .pdf / 图片。`） |
| `none` | 当前合同还没有任何条款修改 |
| `blocked` | 预计有 N 条修改尚未建立可靠原文定位，暂不能安全导出 |
| `ready` | 修改位置已确认，可生成修订版 |

- 格式判断依据是 `contract.stored_path`（**回退**到 `file_name`），因为 `file_name` 常常没有扩展名；
- 按钮「下载修改后的合同」→ `GET /contracts/{id}/revised-docx`（blob），另存为 `<名称>_修订版.docx`；
- 前端状态只用于**提示**，**权威判定始终在下载端点**。因此 `ready === true` 仍可能因新增条款位置不可解析而返回 400；此时应原样展示后端 `detail`。

## 六、R09 缺失条款的补充逻辑

R09（不可抗力条款缺失）当前**不是简单给一个风险结论**，而是一条可操作的补充链路。

### 6.1 建议来源

`POST /api/contracts/{id}/add-clause-suggestion`（`AddClauseSuggestionRequest`：`risk_type` 默认 `"R09"`，`instruction` 可选）返回：

| 字段 | 来源 |
|---|---|
| `templates` | `search_similar_templates(query, 3)` —— RAG 检索到的相似合同范本（截取 300 字） |
| `legal_basis` | `search_knowledge(query, "laws", 3)` —— RAG 检索到的法律依据 |
| `suggested_position` | `_suggest_position(parsed_text)` —— 建议插入位置（**仅是建议**） |
| `headings` | `_parse_headings(parsed_text)` —— 合同全部顶层标题，供用户选择位置 |

检索词默认按风险类型映射（指令为空时）：`R09 → "不可抗力条款 通知 免责"`（避免拿 `R09` 这种代码去检索）。

### 6.2 建议插入位置的启发式规则（`_suggest_position`）

1. 优先插在**「争议解决」条款之前**（anchor = 争议解决的前一条编号）；
2. 否则插在**「违约责任」之后**；
3. 再否则追加到**合同末尾**；
4. **无标题结构时返回 `None`** —— 此时前端**必须要求用户明确位置**，不会默认放到末尾。

### 6.3 用户可以做的四件事

前端 `InlinePositionPicker.vue` 提供五种位置模式：

| 单选项（原文） | 值 | 说明 |
|---|---|---|
| `使用推荐位置：<hint>` | `suggest` | **接受 RAG/启发式给出的推荐位置**；有建议位置时才渲染；推荐位置只是**候选**，必须点「确认位置」才成立 |
| `在某一编号条款之后` | `after` | **自己选择其它位置**（按条款编号） |
| `在某一编号条款之前` | `before` | **自己选择其它位置**；编译为「第 X-1 条之后」；若选中的是合同第一条，会明确提示 `该条款已是合同第一条，前面无法再插入，请改选其它位置。` |
| `合同末尾` | `append` | 追加到末尾 |
| `用描述定位位置` | `locate` | **自己描述插入位置**：自由文本 → 只读定位接口 `POST /locate-clause` → 候选列表 → 逐个「选为插入位置」 |

组件内明确定义的两条边界：

- **没有推荐位置时绝不自作主张**（尤其不许默认 `append`）；
- 描述定位只调**只读** locate 接口，候选**必须用户点选**。

> **「暂不修改」的实际形式**：不生成、不确认即可——**不存在一个叫「跳过」的位置单选项**。用户选择不继续时，只需不点「生成推荐草案」/「确认新增」；该条款会一直停留在会话列表的「新增条款」组里（状态文案 `待新增（需确认插入位置）`），不产生任何落库记录、不影响导出。总体方案的逐项处理里有明确的「跳过」按钮（语义为「本轮暂不采用，不会永久关闭或删除这条风险」），那是**方案层**的跳过，不是位置选择项。

### 6.4 统一进入现有修改会话体系

R09 补充**不是第二套独立修改系统**：

- 生成或保存时提交的就是普通的 `POST /{id}/revise`，只是 `operation = "add_clause"`、`clause_text = ""`、`position = 用户确认的位置`；
- 落库进的就是 `clause_revisions` 表，`scope` 沿用当前会话的 scope；
- 多轮调整同样按 `clause_key` 分组，同一位置只保留最新版本；
- 确认采用走的是同一套采用态机制（新增条款的前置校验是「插入位置可解析」）。

### 6.5 其他缺失型风险的复用

`add-clause-suggestion` 的 `risk_type` 不限于 R09，代码内置的检索词映射覆盖 `R09/R08/R10/R11`，其余类型回退为「缺失条款」。因此新增条款能力对所有「缺失型」问题（例如条款比对判定为 missing 的标准条款）同样可用。

## 七、原文定位工具（`POST /contracts/{id}/locate-clause`）

这是修改系统的基础设施，**只读**：不调 LLM、不写数据库、不新建/修改任何 `ClauseRevision` / `AuditRecord` / `AuditReport`，可安全重复调用。

请求：`{ "text": "用户选中的逐字原文或自然语言描述", "clause_anchor": "五" }`

定位优先级：

1. **条款编号锚点**：`clause_anchor` 按「第X条」定位整条（支持中文/阿拉伯数字），窗口从标题起点到下一个「第X条」标题，上限 1200 字；
2. **原文精确匹配**：`text` 唯一命中直接返回；多处命中复用 `_pick_best_hit` 的「（N）子项」消歧；仍无法唯一消歧则返回候选列表让用户选；
3. **前缀匹配**：原文被改写/重组时按前缀逐级缩短匹配；
4. **关键词匹配**（自然语言描述）：纯确定性字符串处理——按非中英数边界切词、去停用词、整段不命中时回溯寻找「最长且确实出现在正文里」的子串；打分优先「只出现一次」的 token，其次更长 token。

返回 `{found, clause_no, clause_title, original_text, start, end, match_mode, candidates, reason}`。

**语义要点**：只有 `data.original_text` 才是可以提交给 `POST /revise` 的**逐字原文**；其余候选与描述只用于展示。`found=True` 只表示「在正文中定位到候选」，**不代表后端已建立 revision 锚点**——锚点仅由 revise 端点写库时建立。

## 八、总体修改会话的 API 一览

| 方法 | 路径 | 调 LLM | 写库 |
|---|---|---|---|
| GET | `/api/contracts/{id}/overview` | 否 | 否（纯只读） |
| POST | `/api/contracts/{id}/overview/plan` | 是（1 次） | 只写方案表 `revision_proposals` |
| GET | `/api/contracts/{id}/overview/proposals` | 否 | 否 |
| GET | `/api/contracts/{id}/overview/proposals/{pid}` | 否 | 否 |
| POST | `/api/contracts/{id}/overview/confirm` | 否 | **写 `ClauseRevision`** |

`/plan` 的语义要点：

- 不再把整份合同重写存成 `overview+replace` 讨论稿，而是产出**逐项修改清单**；
- 整份合同正文进入 prompt 的预算是 **24000 字符**；超出时**不静默截断**，而是降级为「标题结构纲要 + 当前审核风险条目」并在上下文里显式标注 `contract_text_truncated`；
- 一次最多保留 **30 项**；`revised_clause` 为空的项被丢弃；全部项无效 → 502；
- 每一项都由后端做**确定性定位**（replace → 逐字原文锚点；add_clause → 插入位置），`resolved=false` 的项必须由用户先确认位置才能进入确认落库。

`/confirm` 的语义要点：只接受 `resolved=true` 的项；**不调用 LLM**（方案内容已是最终文本）；**逐项独立事务**，一项失败不影响其它项；落库即 `adopted=True`（与「确认采用此版」同一语义，不引入第二套确认概念）。

`GET /overview` 返回的每个专项会话包含：`original_text`（当前原文）、`original_source`（`anchor`/`first`/`none`，表示该值的可信度）、`revised_clause`（当前最新修改结果）、`legal_basis`、`remaining_risks`、`located`、`location_state`（`located`/`pending`/`none`）、`export`（该会话的 DOCX 状态与阻塞原因）。

详见 [`总体会话-后端API契约.md`](./总体会话-后端API契约.md)（该文件是接口契约的完整字段级说明）。

## 九、当前修改系统的真实局限（如实列出）

1. **修订版统一输出 DOCX**：DOCX / 普通 PDF / 扫描 PDF / JPG / PNG / TIFF / BMP 均可经「审核 → 修改 → 导出修订版 DOCX」；非 DOCX 输入由 `parsed_text` 重建**中间 DOCX** 后再应用修订。系统**不提供** PDF→PDF 或图片→图片导出，也不支持导出「未修改的原件」。
2. **不生成 Word 修订痕迹（Track Changes）**。导出的是「已应用修改的正式文本」。
3. **不做完整版本管理**。`clause_revisions` 是轻量修订记录表，不是版本控制系统；同一 `(contract_id, clause_key)` 只标记一个「采用版本」，其余轮次仅作为历史保留。
4. **同一段原文被两个不同会话都确认采用时**，DOCX 归并按锚点后写覆盖（已知边界，本轮未处理）。
5. **「确认新增」与「确认采用此版」是两个不同动作**，语义不可混用（见 4.6）。
6. **新增条款的位置选择没有独立的「取消本次新增」按钮**：用户通过不提交来表达拒绝；未选定合法位置时后端也会拒绝采用该 `add_clause` 修订。
